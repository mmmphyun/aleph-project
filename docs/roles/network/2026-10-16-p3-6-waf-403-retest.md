## 1. 선행 장애와 재실측 조건

[모바일 초회](2026-10-16-p3-6-waf-measurement.md)는 입력 계약 오류와 출발지 IP 분산을 확인했다. [고정 IP 첫 재실측](2026-10-16-p3-6-fixed-ip-retest.md)은 클라우드 A 확인상 입력 파싱과 `WEB_DIRECTORY_SCANNING` 탐지에 성공했으나, `wafv2:GetWebACLForResource`의 `AccessDeniedException`으로 IPSet 등록 전에 중단됐다.

사용자가 클라우드 A의 Lambda 조회 권한 핫픽스 배포 완료와 동일 조건의 1회 재실측 요청을 전달했다. 기존 일회용 Ubuntu 노드에서 같은 스크립트를 한 번 더 실행했다. 네트워크 담당은 IAM·계약·수집·탐지·차단 엔진·인프라 코드를 수정하지 않았다.

- 승인 origin: `http://cloudshield-alb-dev-308142572.ap-southeast-2.elb.amazonaws.com`
- 코드: `2eb0e22c6076dc82a257d932c21753acb0f2f89a`의 `network/web_dir_scan.sh`
- 실행 조건: `--tool curl --candidates 15 --interval 1 --max-runtime 60 --execute`
- 공인 IP: 전·중·후 외부 조회 모두 `3.26.171.60`; 완료 관측 시각 17:09:42.643 / 17:09:50.372 / 17:10:29.711 KST
- 캡처: `ens5`, `ip and tcp and port 80`, snaplen 4,096바이트, 최대 2,000패킷·90초, `--immediate-mode`, `-U`

## 2. HTTP 응답 전환

모든 시각은 2026-10-16 KST다. 아래 응답 시각은 PCAP frame 시각이며 클라이언트 프로세스 종료 시각과 구별한다.

| 요청 | PCAP 응답 시각 | 상태 / 의미 |
| --- | --- | --- |
| 사전 HEAD `/` | 17:09:42.764241 | 200, 시작 전 정상 |
| GET 15건 | 스캔 프로세스 17:09:42.766~17:09:59.091 | 401 1건, 404 13건, 200 1건; 스캔 안의 403은 0건 |
| 종료 약 3초 후 HEAD `/` | 17:10:02.136695 | 200 |
| 종료 약 10초 후 HEAD `/` | **17:10:09.112252** | **최초 관측 403**, frame 176 / TCP stream 17 |
| 종료 약 20초 후 HEAD `/` | 17:10:19.119081 | 403 |
| 종료 약 30초 후 HEAD `/` | 17:10:29.118612 | 403 |

전체 20개 요청·응답(GET 15 + HEAD 5)을 PCAP에서 모두 짝지었다. 전체 응답 분포는 200 3건, 401 1건, 404 13건, 403 3건이다. **스캔 중 차단됐다고 기술하지 않는다.** 최초 403은 사후 정상 확인용 HEAD에 대한 응답이다. 해당 403은 4절의 클라우드 A 원본 로그 대조 결과상 WAF `action=BLOCK`, `clientIp`, `terminatingRuleId`와 일치한다.

17:10:02의 200과 17:10:09의 403 사이에는 연속 요청을 하지 않았다. 따라서 최초 관측 403을 정확한 정책 적용 시각으로 동일시하지 않으며, ALB 각 경로의 전파 완료 시각도 단정하지 않는다.

## 4. 클라우드 A 로그 대조와 대응 시간 해석

아래 클라우드 항목은 사용자가 전달한 클라우드 A의 CloudWatch·Lambda 런타임 로그 전수 대조 결과다. 네트워크 담당이 AWS 원본을 직접 조회한 것은 아니다. 클라이언트 항목은 보존한 PCAP을 직접 분석했다.

| 단계 | 시각 / 결과 | 근거 |
| --- | --- | --- |
| 첫 GET `/admin` 송신 | 17:09:42.787941 | PCAP |
| 다섯 번째 의심 경로 `/backup` 송신 | 17:09:48.563249 | PCAP; 첫 의심 GET과 5.775308초 간격 |
| Lambda 실행 | 17:09:50.915~17:09:52.314, **1.399초** | 클라우드 A; RequestId `1f089011-c024-40d9-92a6-852d14833b73` |
| 탐지 | `WEB_DIRECTORY_SCANNING` 정상 판정 | 클라우드 A; 별도의 정확한 판정 시각은 미제공 |
| IPSet 갱신 | 17:09:52, `3.26.171.60/32` 등록 완료 | 클라우드 A; 초 단위 시각 |
| Slack 발송 | 17:09:52, HTTP 200; WEB_DIRECTORY_SCANNING → BLOCK_WAF 카드 정상 | 클라우드 A; 실제 사용자 수신 시각은 별도 미제공 |
| 이후 정상 응답 | 17:10:02.136695, HTTP 200 | PCAP |
| 최초 WAF BLOCK | 17:10:09.112, `clientIp=3.26.171.60`, `action=BLOCK`, `terminatingRuleId=CloudShield-Block-IP` | 클라우드 A의 WAF 원본 로그 대조 |
| 최초 HTTP 403 수신 | 17:10:09.112252 | PCAP; 클라우드 A의 BLOCK 시각과 밀리초 단위 일치 |

고정 출발지에 대한 **WAF 기능 차단 성공은 확인됐다.** 시간 지표는 다음처럼 구분한다.

1. Lambda 전체 실행은 1.399초이며, IPSet 갱신과 Slack 발송이 같은 실행 구간에 완료됐다는 클라우드 A 결과를 전달받았다. 첫 공격 GET부터 Lambda 실행 완료까지는 **9.526059초**다. 이는 탐지·제어 API·발송 처리 구간의 완료 증거이며 실제 HTTP 차단 반영의 완료 시각은 아니다.
2. 첫 GET부터 최초 403 관측까지 **26.324311초**, 다섯 번째 의심 GET부터는 **20.549003초**, Lambda 시작부터는 **18.197252초**였다. 클라이언트 프로브에는 빈 구간이 있으므로 최초 관측 403을 실제 정책 적용의 정확한 시작 시각으로 취급하지 않는다.
3. Lambda 시작 후 약 11.222초인 17:10:02.136695에도 실제 200 응답이 있었다. 따라서 **제어 API 완료 또는 Slack 발송을 실제 데이터 경로 차단 완료와 동일시하거나, 이번 결과를 전체 HTTP 차단 경로의 10초 SLA 완전 입증으로 보고하지 않는다.** 정확한 탐지 판정 시각, SLA 시작·끝 정의 및 정책 반영 구간은 클라우드 A와 별도 확정해야 한다.

AWS는 IPSet 변경 전파에 수초에서 수분이 걸릴 수 있으며, 같은 새 주소가 일부 영역에서는 차단되고 다른 영역에서는 일시적으로 허용될 수 있다고 설명한다. 이번 API 완료와 응답 전환의 차이에 전파 지연이 포함됐을 가능성은 있지만, 이 자료만으로 지연 전체의 원인을 확정하지 않는다. [AWS UpdateIPSet 공식 문서](https://docs.aws.amazon.com/waf/latest/APIReference/API_UpdateIPSet.html)
