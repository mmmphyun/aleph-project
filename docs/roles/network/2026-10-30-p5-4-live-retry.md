외부 연속 SSH PCAP은 258프레임이다. 기준선 SYN→SYN-ACK→ACK, 첫 timeout 탐침의 SYN 단독, 복구 후 신규 handshake를 동일 호스트 탐침 구간과 TCP stream으로 연결했다. 각 단계 프레임 번호는 ['1', '2', '3'] / ['213'] / ['252', '253', '254']이다. 탐침 종료 시각이 밀리초 단위로 잘려 있어 비교 상한을 1ms 넓히고 그 해상도를 증거에 명시했다. 공개 증거에는 실제 IP·리소스 ID를 넣지 않았다.

## Web 중단 원인과 A에게 필요한 확인

두 ALB 주소의 PCAP에 각각 SYN 7개·응답 0개를 확인했다. HTTP HEAD 자체도 네트워크에 송신되지 못했고 GET 스캔은 시작하지 않았다. WAF가 이번 Web 공격을 차단했다는 증거가 아니다.

승인된 공격 노드 SG는 전체 송신을 허용한다. 타깃 VPC에서 이름/설명에 ALB가 들어간 SG를 조회하니 TCP 80 ingress는 이전 시험 출발지 /32만 허용하고 현재 공격자 /32는 없었다. 실제 ALB와 이 SG의 결합은 별도 API로 확인하지 않았으므로 소유자 확인이 필요하다.

> A에게: 승인 ALB의 실제 연결 SG를 확인하고 현재 전달받은 공격자 공인 IP /32의 TCP 80을 허용해 주세요. ALB 두 주소에서 SYN 응답이 없습니다. 허용 규칙과 정상 HTTP 200 기준선을 확인하면 새 승인으로 Web만 재실측하겠습니다. 에이전트는 SG 규칙을 변경하지 않았습니다.

## 최종 상태와 남은 증명

SSH 원본 17개와 Web 원본 14개, 총 **31개를 회수해 SHA-256 전부 일치**를 확인했다. 최종 타깃은 Baseline SG이고 WAF에 현재 출발지 차단이 남아 있지 않다. Web 실패 때문에 전체 컨트롤러 complete=false/exit 3이며 자동 재공격하지 않았다.

SSH 키 인증은 선택 해제했으므로 null이다. 첫 실제 공격 패킷·장비 간 시계 최대 오차·Slack 전체 3단계 원본 ts·Web 왕복·WAF BLOCK 원문은 미확보다. 서버의 2.7694초를 전체 10초 SLA 충족으로 쓰지 않는다. 이 후속 변경은 결과 문서와 선별 증거만 추가하며 코드·테스트·인프라를 수정하지 않는다.
