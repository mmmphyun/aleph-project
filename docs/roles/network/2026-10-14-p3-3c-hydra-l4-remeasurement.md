### 연결 차단을 어떻게 확인했나

| 관측 | 쉽게 설명하면 | 이번 결과 |
| --- | --- | --- |
| SYN | 클라이언트가 보내는 "연결해도 될까요?" 요청 | 매초 새 연결로 확인 |

| 복구 후 TCP 연결 | 원래 규칙으로 돌아온 뒤 접속 가능 여부 | 단일 nc 확인 성공 |

이 결과는 **새 TCP 연결의 차단**을 확인한 것이다. 이미 로그인해 유지 중이던 SSH 세션이
끊기는지는 이번에 측정하지 않았다. 무응답 원인은 네트워크 증거만으로 확정하지 않고 A의
격리 SG 확인값과 대조해 해석한다.

## 1. 결과 및 한계

공격 전 TCP 22 기준선이 정상 연결됐다. Hydra는 합성 후보 5개를 소진하고 인증 성공 없이
종료했다. 1초 간격 신규 연결 탐침 60회 중 앞의 24회는 연결됐고 뒤의 36회는 모두 0.8초
타임아웃으로 끝났다. PCAP에서는 후반 36개 스트림에 출발 SYN만 있으며 SYN-ACK와 RST는
없다. 캡처된 패킷은 328개, 커널 드롭은 0개다.

이는 신규 TCP 연결의 무응답 전환을 증명한다. 사용자 경유 클라우드 A/B 실측 요약에서는 서버
실패 5건과 Quarantine SG 부착이 보고됐다. 아래는 그 요약과 로컬 PCAP의 대조 결과이며,
서버·AWS 원본을 네트워크 담당이 독립적으로 확보한 것은 아니다. 후보 개수·SSH 스트림 수·
암호화된 페이로드 수를 서버 실패 횟수로 대신하지 않는다. 기존 인증된 SSH 세션은 측정하지 않았다.

공격 프로세스 호출 직전부터 첫 무응답 SYN까지는 약 24초다. 따라서 공격 시작을 기점으로 한
신규 TCP 연결의 10초 차단은 관측되지 않았다. A/B 전달값을 기점으로 계산한 5번째 실패부터
SG 확인까지는 3.589초, 최초 무응답 SYN까지는 약 5.478초다. B가 추가 전달한 원본 Slack ts
`1791953274.092879`는 13:47:54.092879 KST의 게시 시각이다. 5회차 실패부터 Slack 게시까지는
5.181879초이며, SG 확인과 게시 두 사건이 모두 끝난 시각도 이 게시 시각이다. 신규 연결
무응답까지 포함한 세 사건의 마지막 관측은 최초 무응답 SYN으로, 약 5.478초다.

공격 첫 SYN부터 Slack 게시까지는 23.639945초, 최초 무응답 SYN까지는 23.936051초로 모두
10초를 초과했다. 따라서 이번 실행의 공격 시작 기준 10초 목표를 달성했다고 표현하지 않는다.
임계값 충족 이후 대응은 기록된 시각 기준 10초 이내지만 Slack 클라이언트 실제 수신은
측정하지 않았다. 클라우드 A의 "종단간 3.589초"는 `T_sg_verified - T_auth(5회차)`로 한정한다.

복구 완료 통보 뒤 Kali에서 단일 `nc -n -zv -w 3` 연결을 실행해 코드 0과 TCP 22 정상 연결을
확인했다. 확인 완료 시각은 14:35:23.944 KST다. 인증이나 재공격은 실행하지 않았다.

## 2. 이전 실행과 변경 범위

2026-10-13 실행은 후보 5개를 소진했지만 신규 연결 30회가 모두 성공했다. 사용자가 전달한
서버 관측값은 실패 4회이며 원문은 아직 제공되지 않았다. 당시 Hydra는 응답 대기 3초가 짧다는
경고를 남겼다. 이 경고만으로 실패 누락 원인을 확정하지 않는다.

사용자가 재실측과 A/B 준비 완료 및 시간 상한 변경을 승인했다. 응답 대기를 10초, 공격 실행
상한을 60초, 캡처를 75초, 탐침을 60회로 늘렸다. 후보 5개, 동시성 1, 합성 오답, TCP 22
단일 대상, 2,000패킷 상한, 예상치 못한 인증 성공 중단은 유지했다. `-v`로 SSH 모듈 준비와
연결 오류 진단을 남기며 비밀번호를 출력하는 `-V`는 사용하지 않는다.

기존 실행 가드를 삭제하거나 이전 증거를 덮어쓰지 않았다. 이번 승인에 대응하는 새 증거 루트에
별도의 원자적 실행 가드를 만들고 한 번만 실행했다. AWS 설정 변경과 롤백은 수행하지 않았다.

Hydra SSH 구현은 인증 기능 확인 연결과 실제 인증 연결을 구분하며 같은 계정의 연결을 재사용할
수 있다. 이 때문에 TCP 스트림 수가 인증 실패 수와 같지 않다.
근거: [Hydra v9.7 SSH 모듈](https://github.com/vanhauser-thc/thc-hydra/blob/v9.7/hydra-ssh.c).

아니며 메시지 게시 시각에 대한 전달 증거로 기록한다. 네트워크 담당이 Slack API나 원본 메시지를
독립 조회한 것은 아니다. 정확한 소수초는 원본 ts를 기준으로 보존했다.

공격 첫 SYN부터 게시까지는 23.639945초, 5회차 인증 실패부터 게시까지는 5.181879초다.
최초 무응답 SYN은 Slack 게시보다 0.296106초 늦게 관측됐다. 게시 시각을 클라이언트 실제
수신 시각으로 바꾸지 않으며, 게시 기준과 수신 기준의 판정을 구분한다.

B의 Windows 재연결은 14:23:15.184~14:23:15.421 KST, 네트워크의 Kali 재연결은
14:35:23.729~14:35:23.944 KST다. 각각 별도 장비에서 인증 없이 단일 TCP 연결을 확인했다.
B의 작업 공간에 PCAP이 없었던 점은 네트워크 원본 확보와 별개다. 네트워크 공유값은
`T_attack`(Hydra 첫 SYN) 13:47:30.452934, `T_cut`(첫 무응답 SYN) 13:47:54.388985 KST이며
전환 샘플 구간은 13:47:53.388862~13:47:54.388985다.

### 실습 계정 확인 항목

5건 모두 `Failed password for invalid user cloudshield_test ...` 형식이라고 보고됐다.
계정 부재뿐 아니라 SSH 접근 정책 등에 따른 거부일 수 있으므로 원인을 단정하지 않는다.
B는 계정 조회 실패 로그까지 확인했으나 EC2 접속 권한이 없어 정확한 원인은 여전히
미확정이라고 추가 전달했다. 계정 부재가 확정된 것으로 쓰지 않는다.
타깃 운영자는 `id cloudshield_test`, `sudo passwd -S cloudshield_test`, 유효 SSH 정책과
동일 구간 sshd 오류를 확인해야 한다. 확인과 서버 설정 조치는 클라우드 B/타깃 운영자 범위다.
네트워크 담당은 초기화 스크립트·계정·SG·Lambda 설정을 변경하지 않는다.
