- 추가 공격·복구·Slack 재전송 없이 기존 사건을 읽기 전용 조회했다. 6개 카드의 원래 게시 순서를 유지한다.

## Slack 사건 ID와 실제 게시 시각

두 사건을 각각 검색해 3개 메시지를 찾고 해당 채널·실행 구간의 history를 직접 조회했다. 카드 본문과 원본 ts, 메시지 링크를 비공개 원본에 보존했다. 아래 시각은 Slack 게시 시각이며 사용자 단말 수신 시각이 아니다.

| 사건 | 단계 | 원본 Slack ts | 게시 시각 KST | 원문 대조 |
| --- | --- | --- | --- | --- |
| SSH INC-1793351476-8223 | 1차 | 1793351479.883209 | 18:11:19.883209 | 동일 사건·출발지·타깃, BLOCK_AND_QUARANTINE |
| SSH INC-1793351476-8223 | 2차 | 1793351483.444219 | 18:11:23.444219 | 같은 ID의 분석 카드, 아래 Fallback 상태와 대조 |
| SSH INC-1793351476-8223 | 3차 | 1793351548.837439 | 18:12:28.837439 | 설정 복구 확인·실제 통신 회복 확인, 신규 TCP 연결 |
| Web INC-1793352077-8223 | 1차 | 1793352078.509219 | 18:21:18.509219 | 동일 사건·출발지·타깃, BLOCK_WAF |
| Web INC-1793352077-8223 | 2차 | 1793352082.444779 | 18:21:22.444779 | 같은 ID의 분석 카드, 아래 Fallback 상태와 대조 |
| Web INC-1793352077-8223 | 3차 | 1793352108.475439 | 18:21:48.475439 | WAF 해제·실제 통신 회복 확인, 동일 루트 HEAD |

각 사건은 동일 ID로 1→2→3차 순서에 게시됐다. 1·2차 카드의 출발지/타깃은 승인 대상과 일치한다. 3차는 같은 사건 ID·출발지와 독립 통신 회복 결과를 확인했다. SSH 키 인증은 None으로 표시돼 있어 인증 성공으로 해석하지 않는다. 복구 카드의 엔진 보고 시각은 구성 확인 시각이며, 실제 TCP/HTTP 회복 시각과 구분한다.

이번 조회 도구는 카드의 렌더링된 텍스트·원본 ts를 반환했다. 도구 응답 자체와 텍스트를 해시 보존했으며 Slack 네이티브 Block Kit JSON 전체를 반환받았다고 주장하지 않는다. Incoming Webhook 호출 당시 null이었던 원본 ts를 기존 실행 파일에 소급해 덮어쓰지 않고 별도 상관관계 원본으로 연결했다.

## Grafana 동일 구간 화면과 수치

로컬 비공개 관리자 설정으로 로그인한 뒤 기존 P5-2 대시보드를 실측 때 저장한 API 조회와 같은 절대 구간으로 열었다. 실제 브라우저 스크린샷과 렌더링된 접근성 텍스트를 각각 보존했다. 원본 이미지에는 비공개 식별자가 있어 Git에는 넣지 않고 해시만 공개한다.

| 사건 | 대시보드 구간 KST | 후보 인입 | max/p95 대응 반환 | LLM 최종 상태 |
| --- | --- | --- | --- | --- |
| SSH | 18:09~18:14 | ssh_failures 5 | 2.7694초 | call_failed 1건/100% |
| Web | 18:20~18:23 | http_4xx 14 | 0.4463초 | parse_failed 1건/100% |

화면의 사건 타임라인에서 실제 incident_id·대응 메트릭·1차 Slack 전송 성공·LLM 상태·2차 Slack 전송 성공을 대조했다. Web의 최초 저장 API는 Complete였지만 데이터 프레임이 비어 있었다. 그 원본을 유지하고 동일 구간·동일 5개 쿼리를 재조회해 14건/0.4463초/parse_failed가 실제 화면과 일치함을 확인했다. Complete만으로 사건 데이터 확보를 선언하지 않는다.

## Fallback과 현재 관제 화면의 범위

SSH의 서버 원문은 call_failed/bedrock_call, Web은 parse_failed/response_validation이다. 양쪽 2차 Slack 카드의 제목은 LLM 심층 분석이지만 정상 enhanced 결과는 아니다. Fallback 카드가 게시된 사실과 정상 LLM 보강 성공을 구분한다. 이 관측은 타 직무의 코드나 설정을 변경한 결과가 아니다.

기존 Grafana 사건 타임라인의 조회 결과와 화면에는 로컬 컨트롤러가 전송한 3차 복구 로그 행이 없다. 따라서 3차 카드·복구·통신 회복은 Slack 원문과 컨트롤러/패킷 증거로 연결했으며 Grafana에서 전체 3단계가 표시됐다고 쓰지 않는다. 복구 이벤트를 CloudWatch 대시보드에 함께 표시하는 연계는 A/B 소유 영역의 후속 검토 사항이다.

## 보존·검토 상태

Slack 6개 카드의 원문 텍스트/게시 ts·링크, Grafana 2개 스크린샷/렌더링 텍스트, 동일 범위 재조회 응답과 상관관계 JSON을 Git 밖 비공개 폴더에 보존했다. 공개 JSON은 선택 필드·원본 해시·변환 경계를 기록한다. 조회 중 Slack 메시지를 발송·수정·반응·재게시하지 않았다.

이 대조로 남아 있던 Slack 3단계 원문/게시 ts와 Grafana 화면 확인을 수행했다. 물리적 10초 보장 제약, SSH 키 인증 선택 해제, SSH 첫 실제 공격 패킷·장비 간 정량 시계 오차·동일 연결 재사용의 미확인 범위는 기존 기록대로 유지한다. PR은 리뷰 가능 상태이며 전체 티켓 완료·머지는 별도 판정이다. 후속 변경은 네트워크 문서와 공개 선별 증거뿐이다.
