## 지연 실측과 판정

| 지표 | SSH | Web |

| 첫 실제 공격→첫 차단 후보 | 실제 공격 패킷 특정 미완료/null | **21.291308초**, 실제 GET 프레임 → 같은 루트 HEAD 403 프레임 |

이번 Web 실측은 첫 실제 요청 기준 **10초 SLA를 충족하지 못했다**. 0.4463초는 서버의 탐지→API 반환 구간이므로 전체 관통 지연으로 대체하지 않는다. 원본 타임라인을 나눈 구간은 첫 GET→서버 탐지 6.745574600초, 서버 기록 탐지→API 반환 0.4463초, API 반환→첫 루트 403 관측 14.099472700초다. 장비 간 시계 최대 오차는 미측정이므로 이 분할은 참고값이다. 마지막 구간만으로 WAF 전파 시간을 단정하지 않는다.

## 패킷 근거와 원본 해상도

| Web 단계 | 원본 좌표 | 실제 관측 |
| --- | --- | --- |
| 정상 기준선 | capture-0.pcap frame 6 | HEAD / 응답 200 |
| 첫 실제 공격 | capture-0.pcap frame 14 | GET /admin, epoch 1793352070.710004000 |
| 첫 루트 차단 후보 | capture-0.pcap frame 226 | HEAD / 응답 403, epoch 1793352092.001312000 |
| 해제 후 첫 정상 회복 | capture-0.pcap frame 236 | HEAD / 응답 200, epoch 1793352108.110343000 |

두 ALB 주소의 연속 PCAP은 240/160프레임이며 총 15개 GET을 확인했다. 각 HTTP 응답을 동일 파일의 TCP stream에서 요청 메서드/URI와 연결했다. 원본 PCAP magic이 마이크로초 형식임을 확인했으므로 TShark의 9자리 출력 뒤 000을 나노초 정확도로 해석하지 않고 해상도 0.000001초를 명시했다. 기존 roundtrip_timeline에 해시된 CSV와 원본 좌표 sidecar를 추가한 별도 입력으로 계산했으며 기존 요약을 덮어쓰지 않았다.

SSH handshake 프레임은 이전 보고서의 기준선 1/2/3, timeout 후보 213, 복구 후 252/253/254를 사용한다. Web 요청은 매번 별도 curl 프로세스이므로 같은 keepalive 연결의 응답 전이를 증명한 결과는 아니다.

## 실제 WAF 원문 대조

현재 조회 권한으로 CloudShield의 네이티브 WAF 로그 그룹을 발견해 동일 실행 구간의 출발지 이벤트 40개를 보존했다. 원문의 ALB 식별자·계정·출발지가 승인값과 일치함을 확인했고 ALLOW 38개, BLOCK 2개였다. 두 BLOCK은 CloudShield-Block-IP 규칙의 HEAD /이며 timestamp는 1793352092001 및 1793352103364ms다. 첫 BLOCK의 원문 시각과 PCAP frame 226의 루트 403 시각이 일치한다.

WAF timestamp와 CloudWatch ingestionTime/eventId를 별도로 보존했다. 수집 시각을 집행 시각으로 바꾸지 않는다. native WAF에는 incident_id가 없으므로 동일 출발지·승인 ALB/계정·메서드/URI·실행 구간으로 연결하며, 패킷과 공유하는 request ID를 확보한 것으로 표현하지 않는다.

## 복구·관제·보존

기존 A 복구 함수·B 알림 함수·보안 매퍼를 변경하지 않았다. 실제 서버가 발급한 incident_id를 유지했으며 모의 사건을 주입하지 않았다. 성공 회차 원본은 SSH 17개와 Web 15개, 총 **32개**를 회수해 manifest SHA-256 일치를 확인했다. 이전 실패 회차도 별도로 보존했다. 원본 PCAP·로그·승인·키·웹훅은 Git 밖 비공개 경로에 남긴다.

Web controller complete=true/exit 0, 복구 후 HTTP 200, 같은 사건의 3차 알림 함수 성공을 확인했다. 최종 타깃은 Baseline SG이며 WAF에 현재 출발지 차단이 남아 있지 않다. 각 성공 시나리오의 기존 Grafana 5개 쿼리 Complete 응답을 보존했다. Incoming Webhook 성공은 원본 Slack 게시 ts와 전체 1·2·3차 카드 대조를 대신하지 않는다.

## 남은 DoD와 인계

- A/B와 실제 첫 요청 기준 지연의 수집·집계·집행·전파 구간을 확인한다. 이번 후속 변경에서 플랫폼 코드를 수정하거나 새로운 이슈를 만들지 않았다.
- 실제 WAF BLOCK/ALLOW 원문 대조는 확보했다. B의 Slack 1·2·3차 원문/게시 ts·같은 구간 Grafana 화면 대조가 남아 있다. 현재 403은 실제 네트워크 관측, 서버 BLOCK_WAF 성공, 승인 ALB의 실제 WAF BLOCK 원문을 연결했다.
- SSH 키 인증은 선택 해제 상태여서 null이다. SSH 첫 실제 공격 패킷, 장비 간 시계 최대 오차, 연결 재사용 증거도 미확보다.
- 왕복 동작과 3차 알림 호출은 두 시나리오에서 완료했지만 전체 P5 DoD 및 첫 공격 기준 10초 SLA 완료로 판정하지 않는다. PR은 Draft로 유지한다.

후속 변경은 네트워크 결과 문서·마스킹 증거뿐이다. 코드·의존성·검증 게이트·타 직무 파일을 변경하지 않는다. 기존 구현의 로컬 필수 게이트와 CI 통과 결과는 PR 본문에 유지한다.
