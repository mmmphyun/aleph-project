## 1. 개요: Cloudflare 모델 도입 검토와 공학적 반추

CloudShield의 DynamoDB 인증 실패 누적 윈도우(`AuthFailureWindow`) 설계 과정에서, Cloudflare의 Rate Limiter 표준 알고리즘인 **가중 2-버킷 슬라이딩 윈도우(Weighted Two-Bucket Sliding Window)** 도입을 검토하고 실측 벤치마크를 수행했습니다.

그러나 통계적 근사 모델을 적용한 결과, 실제 침해사고 시나리오에서 **탐지 누락(False Negative) 2건과 오탐(False Positive) 2건이 구조적으로 발생**했습니다. 본 문서는 *"보안 시스템은 왜 항상 100% 정확도를 가질 수 없는가?"*와 *"어떤 조건에서 정확도를 희생하고, 어떤 조건에서 상태를 보존해야 하는가?"*에 대한 저수준 CS 및 시스템 보안 엔지니어링 관점의 분석을 정리합니다.

---

## 2. 보안 3대 요소(CIA Triad)와 계층별 트레이드오프

보안 아키텍처에서 '정확도'와 '가용성'은 상호 배타적인 경우가 많습니다. 시스템이 감당해야 하는 트래픽 볼륨에 따라 최우선 사수 목표가 정반대로 분기됩니다.

```text
[시스템 공격 양상에 따른 보안 엔지니어링 분기]

                 ┌── [초대형 볼륨 공격 (DDoS / Flood)]
                 │   - 위협: CPU/메모리 고갈로 인한 전체 시스템 다운
                 │   - 최우선 가치: 가용성 (Availability)
                 │   - 선택: 무상태(Stateless) / 통계적 근사 (정확도 희생)
                 │   - 기법: SYN Cookie, Token Bucket, NetFlow Sampling
트래픽 볼륨 분석 ─┤
                 └── [저빈도 은닉 공격 (Brute Force / Low-and-Slow)]
                     - 위협: 탐지 임계치 우회 침해 및 정상 사용자 오차단
                     - 최우선 가치: 정밀성 (Precision & Integrity)
                     - 선택: 상태 보존(Stateful) / 타임스탬프 슬라이딩 로그
                     - 기법: Sliding Log, Closed-loop L4/L7 원자적 격리
```

### 2.1 가용성(Availability) 우선: 볼륨성 공격 (Volumetric / DDoS)

공격 트래픽이 초당 수만~수천만 단위에 달할 때, 시스템이 개별 패킷/요청의 타임스탬프나 세션 상태를 저장하려 하면 **방어 시스템(Control Plane)의 메모리와 CPU가 먼저 고갈**되어 서비스가 전면 중단됩니다. 따라서 가용성을 위해 정확도와 상태를 의도적으로 희생합니다.

#### 1) L4 TCP SYN Flood 방어: SYN Cookie (RFC 4987)
* **저수준 메커니즘**:
  * 정상 TCP는 SYN 수신 시 커널 메모리의 SYN 백로그 큐(TCB)에 소켓 상태를 할당함 ($O(N)$ 메모리 소모).
  * 대량의 위조 SYN 인입 시 백로그 큐가 포화되어 커널 OOM이 발생하거나 정상 연결이 거부됨.
  * **SYN Cookie**: 커널이 백로그 큐에 상태를 일절 저장하지 않음 ($O(0)$ 무상태). 클라이언트/서버 소켓 튜플, 시크릿 키, MSS를 단방향 암호화 해시하여 SYN-ACK의 **32비트 ISN(Initial Sequence Number)**에 인코딩해 응답하고 메모리에서 즉시 폐기.
* **희생되는 것 (정확도 및 네트워크 표준 기능의 손실)**:
  * 32비트 ISN 공간 한계로 인해 TCP 고급 성능 옵션인 **Window Scaling, SACK(선택적 재전송), 타임스탬프 정보가 유실**됨.
  * 네트워크 패킷 재전송 처리의 정밀도가 희생되지만, **서버 커널이 죽지 않고 살아남는 가용성**을 사수함.

#### 2) 백본 라우터 NetFlow / sFlow 패킷 샘플링 (RFC 3954)
* **저수준 메커니즘**: 100 Gbps 백본망에서 초당 수천만 pps를 전수 딥 패킷 인스펙션(DPI)하면 CPU 캐시 스래싱과 인터럽트 폭풍으로 라우터 ASIC이 정지함. 따라서 $1/1,000 \sim 1/10,000$ 단위로 패킷을 샘플링하여 통계적 패턴만 추출함.
* **희생되는 것**: 샘플링 오차로 인해 개별 악의적 패킷이 유입되거나 정상 패킷이 일시 드롭될 수 있으나, 백본망의 라우팅 가용성을 보장함.

#### 3) L7 API 게이트웨이: Cloudflare Rate Limiter (가중 2-버킷 모델)
* **저수준 메커니즘**:
  $$\text{Count} = \text{Count}_{\text{curr}} + \text{Count}_{\text{prev}} \times \left(1 - \frac{t_{\text{elapsed}}}{W}\right)$$
  초당 수십만 RPS의 HTTP 요청에 대해 요청 시각을 버리고 정수 카운터 2개만 유지하여 메모리 $O(1)$을 달성함.
* **희생되는 것**: 대규모 트래픽에서는 대수의 법칙으로 오차가 0%에 수렴하지만, 개별 경계면에서 몇 개의 요청이 더 통과(미탐)하거나 정상 요청이 429로 거부(오탐)되는 미세 오차를 허용함.

### 2.2 정밀성(Precision) 우선: 저빈도 은닉형 공격 (Low-and-Slow / APT)

반면, SSH 무차별 대입(Brute Force)이나 다중 계정 패스워드 스프레잉(Spraying)은 대역폭을 채우는 공격이 아닙니다. **보안 탐지 임계치를 우회하기 위해 시간 축으로 길게 늘어지는(Time-dilated) 은닉 침해**입니다.

* **통계적 근사의 붕괴 원인**:
  * CloudShield의 탐지 임계치는 **5분간 5회(Brute Force), 2개 계정(Spraying)**이라는 극단적 소규모 이산 정수(Discrete Small Integer)임.
  * 이 구간에서는 단 1회의 왜곡이 전체 판정의 **20% ~ 50%를 왜곡**함.
* **실제 실측 결함 사례**:
  1. **탐지 우회 (False Negative)**: $t=299$초에 4회, $t=450$초에 1회 발생 ($\Delta t=151$초, 총 5회). 직전 버킷 균등 분포 가정이 개입하여 4회가 $4 \times 0.5 = 2$회로 삭감되어 총 3회로 판정 $\rightarrow$ **침해 인프라 방치**.
  2. **오차단 (False Positive)**: $t=1$초에 4회, $t=302$초에 1회 발생 ($\Delta t=301$초, 최근 300초 내 1회뿐). 만료된 301초 전 이벤트가 가중치 $0.993$으로 합산되어 5회로 판정 $\rightarrow$ **정상 사용자 및 호스트 오차단 (자멸적 DoS)**.
* **엔지니어링 결론**:
  * 저빈도 은닉 공격에서는 통계적 근사를 절대 사용해서는 안 되며, 개별 이벤트의 실제 발생 시각을 보존하는 **타임스탬프 슬라이딩 로그(Sliding Log)**를 사용해야만 함.

## 3. 실무 시스템 엔지니어링: 폐루프(Closed-loop) 아키텍처를 통한 리소스 한계 극복

### 3.1 슬라이딩 로그의 고전적 딜레마
타임스탬프를 리스트로 저장하면 이론적으로 공격자가 초당 수천 건의 로그인을 시도할 때 DynamoDB 아이템 한도(400KB) 초과 및 WCU 비용 급증 위험이 존재합니다.

### 3.2 CloudShield의 해결책: 폐루프 인프라 즉시 차단
CloudShield는 단순 모니터링/SIEM 도구가 아닌 **자동 대응 SecOps 파이프라인**입니다.

```text
[공격 인입] ──► [타깃 EC2] ──► [CW Logs] ──► [Lambda: DynamoDB 슬라이딩 로그]
     ▲                                                │
     │                                                ▼ (임계치 5회 도달)
     └────────── [L4 SG / L7 WAF 원자적 차단] ◄───────┘
                 (이후 추가 패킷 커널 도달 차단)
```

1. **아이템 크기 $O(1)$ 바운딩**:
   * 실패 카운트가 5회에 도달하는 즉시 AWS Boto3를 통해 타깃 EC2의 보안 그룹을 `CloudShield-Quarantine-SG`로 교체하고 WAF IPSet에 `/32` 차단 룰을 등록함.
   * 이후 공격자의 6번째 TCP SYN 패킷은 OS 커널에 도달하지 못하고 인프라 경계에서 폐기되므로, DynamoDB로 인입되는 타임스탬프 리스트는 **최대 5~10개를 초과할 수 없음 ($O(1)$ 바운딩)**.
2. **2-버킷 파티셔닝과 무경합 TTL 회수**:
   * 파티션 키에 시간 버킷(`epoch // 300`)을 포함하여 쓰기 시 조건식 없는 원자적 `list_append`로 충돌률 0%를 유지.
   * 10분 TTL(`expire_at`)을 적용하여 만료 버킷 청소를 DynamoDB 엔진에 위임함으로써 애플리케이션 레벨의 Pruning 경합을 원천 배제.

## 4. 포트폴리오 및 기술 면접 방어 프레임워크

### Q. "대규모 환경에서는 Cloudflare처럼 근사 알고리즘을 쓰는 게 맞지 않나요? 왜 타임스탬프를 썼습니까?"

> **모범 답변**:  
> "보안 시스템의 아키텍처는 공격 트래픽의 볼륨에 따라 우선순위가 갈립니다.  
> 초당 수백만 건이 인입되는 L3/L4 DDoS나 L7 Rate Limiter는 메모리 고갈로 인한 전체 시스템 다운을 방지하기 위해 SYN Cookie나 가중 카운터처럼 **정확도를 희생하고 가용성을 사수하는 무상태 모델**이 정답입니다.  
> 
> 반면 CloudShield가 담당하는 SSH 무차별 대입 및 스프레잉은 **5분간 5건, 2건이라는 극단적 소규모 이산 임계치**를 다루므로 통계적 근사를 적용하는 순간 수학적으로 버스트 누락과 만료 오탐이 발생합니다.  
> 또한 저희 파이프라인은 5회 도달 즉시 L4/L7 인프라 차단이 발동되어 후속 패킷이 커널에 닿지 않는 **폐루프(Closed-loop) 구조**를 갖추고 있습니다. 따라서 타임스탬프를 저장하더라도 아이템 크기가 최대 5~10건으로 엄격히 제한되므로, 리소스 팽창 없이 충돌률 0%와 탐지 정밀도 100%를 동시에 달성할 수 있어 슬라이딩 로그를 채택했습니다."
