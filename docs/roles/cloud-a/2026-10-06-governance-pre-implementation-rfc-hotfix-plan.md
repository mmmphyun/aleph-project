## 1. 배경 및 문제 진단 (Post-Mortem: PR #135 사례 분석)

### 1.1 현상
* PR #135(Web L7 관통 오케스트레이터) 구현 시, 1차 및 2차 수정본 모두 로컬 단일 게이트(`check.ps1`, 667개 테스트)를 100% 통과했음에도 리뷰어(네트워크 담당)로부터 2회 연속 Changes requested를 수신함.
* 결함 원인:
  1. **분산 무상태성 결여**: AWS Lambda 런타임의 컨테이너 격리 특성을 간과하고 파이썬 프로세스 힙(`_GLOBAL_WEB_WINDOW`, `defaultdict`)에 상태를 저장하여 다중 실행 환경 간 3+2 분할 배치 미탐지.
  2. **시계열 스트림 사전 소각**: 배치 내 최신 타임스탬프(`max(ts)`) 기준으로 윈도우 밖 데이터를 일괄 삭제하여 0~4초 공격 후 30초 지연 요청 혼합 시 선행 유효 공격 소각.
  3. **테스트 하네스의 확증 편향**: 동일 인스턴스 객체를 두 번 주입하는 Happy Path 테스트를 작성하여 스스로의 결함을 감지하지 못함.

### 1.2 왜 "사전 지시 고도화"나 "2줄 앵커"로는 해결되지 않는가?
* **팀 전문성의 현실**: 학부생 취준생 팀원들이 작업 착수 전에 분산 런타임 동시성 모델, Boto3 예외 격리, 시간순 시계열 인과관계를 미리 예측하여 정밀한 NFR 지시서를 작성하는 것은 불가능함.
* **단순 앵커의 한계**: `AGENTS.md`에 특정 규칙 1~2줄을 추가하는 것만으로는 보안(ReDoS), 클라우드 B(로그 버퍼링), 네트워크(패킷 시퀀스) 등 타 도메인의 잠재적 장애 모드를 방어하지 못함.
* **근본 원인**: 코드를 작성하기 전에 에이전트가 **"해당 도메인의 장애 모델과 엣지 케이스"**를 자가 검토하는 시스템적 안전장치(Pre-flight Check)가 부재함.

## 2. 핵심 해결책: 사전 구현 RFC(Pre-implementation RFC) 프로토콜

에이전트가 노션 카드를 수신했을 때 **곧바로 코드를 작성하지 못하도록 차단**하고, 반드시 아래 3대 요소를 5줄 이내로 브리핑하여 사용자 승인을 득한 뒤 구현에 착수하도록 거버넌스를 강제함.

```text
[작업 착수 흐름 변경]
AS-IS: 사용자 작업 지시 -> 에이전트 즉시 코딩 -> 로컬 Happy Path 테스트 통과 -> PR 제출 -> 리뷰어 결함 지적
TO-BE: 사용자 작업 지시 -> 에이전트 3대 장애 모델 브리핑 (Pre-flight RFC) -> 사용자 승인 -> 견고한 구현 -> 1회 통과
```

## 3. 거버넌스 변경 명세

### 3.1 [`AGENTS.md`](file:///c:/work/aleph-project/AGENTS.md) 2.1조 수정 (제4항 개정)
* **현행**:
  > 4. 설명 선행 원칙: 코딩을 시작하기 전, 해당 작업의 핵심 개념과 원리를 사용자에게 2~3줄로 먼저 설명하여 담당자의 기술 이해도 및 면접 역량을 지원한다.
* **개정 (Pre-implementation RFC 의무화)**:
  > 4. **사전 구현 RFC 및 3대 장애 모델 브리핑 강제 (Pre-implementation RFC)**:
  >    - 에이전트는 코드를 한 줄이라도 작성하기 전, 반드시 아래 3대 항목을 5줄 이내로 요약하여 사용자에게 먼저 보고하고 승인을 받은 뒤 착수해야 한다:
  >      1. **인프라 런타임 제약**: Lambda 무상태(Stateless), 프로세스 메모리 격리, 외부 공유 저장소(DynamoDB) 필요 여부.
  >      2. **잠재 엣지 케이스 2선**: 분할 인입(3+2), 시계열 지연/역전, 비정상 과대 페이로드 등 실패 모드.
  >      3. **적대적 테스트 설계**: 구현 가설을 반증(Falsify)하기 위한 독립 인스턴스 모의 및 장애 주입 테스트 계획.
  >    - 사용자의 승인("진행해", "ㅇㅇ" 등)이 떨어지기 전에는 파일 생성/수정 도구를 호출하지 않는다.
