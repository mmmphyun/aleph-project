## 1. 배경 및 문제 제기

### 1.1 CI 실패 현상 및 초기 원인 (Incident)
- 커밋 `280a020` CI 실행 중 `tests/unit/test_auth_window.py::test_concurrent_record_failure_race_condition`에서 `AssertionError: assert 4 == 5` 간헐적 실패 발생.
- 5개 스레드가 동일 파티션 키(`SPRAY#<ip>`)에 동시 인입될 때, 낙관적 동시성 제어(OCC) 재시도 소진으로 1건의 계정 누적이 유실(Lost Update)되어 단언문 실패 발생.

### 1.2 핵심 3대 트레이드오프 딜레마
1. **지연시간 예산 (10초 관통 SLA)**: DynamoDB 원자적 집계 및 차단 결정은 전체 파이프라인의 극히 일부(수십 ms 이내)를 소모해야 함.
2. **동시성 충돌 (Race Condition)**: 복수의 Lambda 인스턴스가 단일 IP에 대해 밀리초 단위로 동시 인입될 때 데이터 유실(충돌률 0%)이 없어야 함.
3. **탐지 정확도 (Detection Accuracy)**: 5분(300초) 윈도우 경계면 및 비균등 버스트 트래픽에 대한 탐지 누락(False Negative)과 오탐(False Positive)이 없어야 함.

## 2. 아키텍처 대안 4종 설계 및 수학적 모델

### 2.1 대안 A: 단일 키 슬라이딩 윈도우 + OCC (초기 구조)
- **구조**: 단일 파티션 키(`BF#<ip>#<user>`), DynamoDB `UpdateItem`의 `ConditionExpression`을 통한 윈도우 만료 판별 및 신규 개설.
- **동시성 모델**: 충돌 발생 시 `ConditionalCheckFailedException`을 캐치하여 최대 $K$회 재시도 (마이크로 지터 5~25ms 적용).
- **한계**: 스레드 증가 시 재시도 소진으로 인한 데이터 유실(Lost Update) 및 테일 레이턴시 스파이크.

### 2.2 대안 B: 고정 텀블링 윈도우 (Fixed Tumbling Window)
- **구조**: 시간 버킷 파티션 키(`BF#<ip>#<user>#{epoch // 300}`).
- **동시성 모델**: DynamoDB 네이티브 `ADD` 연산자를 활용한 조건식 없는 락 프리 원자적 Upsert.
- **한계**: 경계면 분할(Boundary Split). 경계면 통과 시 카운트가 분할되어 실제 임계치(5회) 공격에 대해 **100% 탐지 누락 발생**.

### 2.3 대안 C: 가중 슬라이딩 윈도우 (Weighted Two-Bucket Counter / Cloudflare 모델)
- **구조**: 시간 버킷 파티션 키 + 선형 시간 감쇠 가중합 추정:
  $$\text{Estimated Count} = \text{Count}(B_c) + \text{Count}(B_{p}) \times \left(1 - \frac{t_{\text{current}} \bmod 300}{300}\right)$$
- **구조적 결함 원인 (통계적 근사의 붕괴)**:
  - 대규모 트래픽($N \gg 1000$)에서는 대수의 법칙으로 오차가 0%에 수렴하나, **극단적 소규모 이산 임계치($N=5, 2$)**에서는 단 1회 왜곡이 20~50% 오차를 유발함.
  - 직전 버킷이 **균등 분포(Uniform Distribution)**되어 있다는 가정이 보안 공격 특유의 **비균등 버스트(Burst)** 인입에서 완전히 깨짐.
  - 실측 결과: 151초 내 5회 집중 공격 탐지 누락(FN 2건), 301초 전 만료 이벤트로 인한 오차단(FP 2건) 발생.

### 2.4 대안 D: 3-버킷 파티셔닝 기반 타임스탬프 슬라이딩 윈도우 (Sliding Log over Three-Buckets, 최종 채택)
- **구조**: 시간 버킷 파티션 키(`epoch // 300`) + 버킷 내 이벤트 타임스탬프 리스트 원자적 append.
- **동시성 모델**: 조건식 없는 원자적 `UpdateItem` (`list_append(if_not_exists(timestamps, :empty), :new_ts)`) $\rightarrow$ **충돌률 0%, 재시도 0회**.
- **판정 모델**: 직전($curr - 1$), 현재($curr$), 직후($curr + 1$) 3개 버킷을 일괄 조회하여 지연/역순 인입된 배치까지 수집하고, 수집된 이벤트 타임스탬프 기준 양방향 유효 구간($ref - 300 \le t \le ref$)을 정밀 필터링 $\rightarrow$ **탐지 정확도 100% (역순 누락 0, 미래 오탐 0)**.

## 5. 엔지니어링 심층 분석: 대안 D의 실무 스토리지 방어 논리

### 5.1 폐루프 차단 아키텍처(Closed-loop Feedback)에 의한 아이템 크기 수렴 특성
* **우려**: 타임스탬프 리스트를 누적하면 대규모 공격 시 DynamoDB 아이템 한도(400KB)에 도달할 위험이 있는가?
* **엔지니어링 팩트 및 실제 제약**:
  * 본 수치는 코드 레벨의 절대적 하드 상한(Hard Limit)이 아닌, **정상 차단 성공 시 폐루프 피드백에 의해 도달하는 운영적 수렴 범위**임.
  * 오케스트레이터는 배치 전체를 먼저 DynamoDB에 기록(`record_failure`)한 뒤 차단을 판정하므로, 단일 배치에 20건이 인입되거나 차단 API 실패 후 재시도되는 예외 상황에서는 리스트 크기가 10개를 초과할 수 있음.
  * 다만 정상적인 운영 상태에서는 임계치(5회) 도달 즉시 타깃 EC2의 L4 보안 그룹(SG) 또는 WAF IPSet에서 해당 IP가 차단(Quarantine)되어 커널 레벨에서 TCP SYN 패킷이 폐기되므로, 추가 실패 로그 유입이 차단되어 일반적인 환경에서 단일 레코드 크기가 5~10개 내외로 자연 수렴함.

### 5.2 TTL 기반 비동기 메모리 회수
* 버킷별 10분 TTL(`expire_at = (bucket_id + 2) * window_seconds`)을 적용하여, 만료된 오래된 버킷 데이터는 DynamoDB 백그라운드 엔진이 자동 소각함.
* 인라인 삭제(Pruning)를 위한 조건부 쓰기 경합을 유발하지 않으며 스토리지 누수를 원천 방지함.

### 5.3 분산 큐의 순서 역전 물리 메커니즘과 3-버킷 스캔의 호출 특성
* **물리 메커니즘**: CloudWatch Logs 구독 필터는 로그 볼륨에 따라 복수의 독립된 Lambda Worker(Firecracker MicroVM 컨테이너)를 병렬 기동함. Worker 간 콜드 스타트 편차(VPC ENI 바인딩 1~2초 지연) 및 네트워크 재전송에 의해 $t=450$이 $t=299$보다 먼저 DynamoDB에 도달하는 물리적 시간축 역전(Time Inversion)이 발생함.
* **DB 호출 특성 (정밀 측정)**:
  * 3-버킷 스캔은 `BatchGetItem`이 아닌 단일 `GetItem`을 직전/현재/직후 버킷에 대해 각각 수행함.
  * 따라서 BF 검사 시 3회의 `GetItem`, 필요 시 Spray 검사 시 3회의 `GetItem`이 순차 실행되어 **총 3~6회의 읽기 RTT(약 6~18ms)**가 발생함 (단일 RTT가 아님).
  * 10초 관통 SLA 대비 여전히 0.2% 미만의 극히 낮은 지연이지만, 향후 고부하 최적화 시 `BatchGetItem`으로의 통합을 고려할 수 있음.

### 5.4 check_threat의 멱등성 조기 탈출(Short-circuit)과 차단 API 호출 억제
* **동작 원리**: 뒤늦게 들어온 지연 로그는 DB 감사 및 누적을 위해 `record_failure()`로 영속화되지만, 직후 평가인 `check_threat()`에서 3개 버킷 중 어느 하나라도 `quarantined == True`가 확인되면 `(False, None, "")`을 즉시 반환함.
* **효과와 범위**:
  * 억제되는 것은 외부 AWS 인프라 차단 API(`apply_remediation`, EC2 SG 교체 및 WAF IPSet 갱신) 호출임.
  * DB 읽기 호출(GetItem) 자체는 상태 확인을 위해 여전히 발생하며, BF가 이미 격리되었더라도 Spraying 격리 여부 확인을 위한 Spray 버킷 조회가 이어질 수 있음. 이를 통해 불필요한 Boto3 차단 API 중복 호출과 AWS API Rate Limit 소모를 정확히 차단함.

### 5.5 지연 로그 및 혼합 배치의 지원 범위와 운영 한계
* **지원 보장 범위**:
  * **인접 버킷($curr \pm 1$, 기준 시각 대비 $\pm 300$초 이내) 내의 역순/지연 배치 인입**.
  * 별도 Lambda 인스턴스 간 $t=450$ 선행 인입 후 $t=299$ 지연 인입과 같은 일반적인 네트워크 재전송 및 콜드 스타트 편차를 100% 탐지 보장함.
* **비지원 및 한계 (운영 제약)**:
  * 단일 배치 내 이벤트 타임스탬프 스팬이 300초(또는 600초)를 초과하는 **장기 지연 혼합 배치** (예: 단일 배치 내에 $t=299$ 4건과 $t=901$ 1건이 공존하는 경우).
  * 현재 오케스트레이터는 배치의 마지막 수신 시각을 기준으로 인접 3-버킷을 평가하므로, $t=901$을 기준으로 버킷 [2, 3, 4]만 스캔하여 버킷 0의 $t=299$는 평가 대상에서 제외됨.
  * 정상적인 CloudWatch Agent 플러시 주기(수 초 단위)에서는 이러한 600초 초과 혼합 배치가 발생하지 않으나, 대규모 인프라 장애 후 장기 버퍼가 일시 플러시되는 특수 환경을 지원하려면 '배치 내 고유 시간대별 개별 윈도우 스캔'으로의 추가 확장이 필요함 (현 마일스톤 제약으로 명시).

---

## 6. 결론

Cloudflare의 가중 2-버킷 모델은 대규모 L7 트래픽 제어($N \gg 1000$)에서 메모리 $O(1)$을 위해 정확도를 희생한 모델입니다. 극단적으로 작은 이산 임계치($N=5, 2$)를 다루는 보안 침해 대응 도메인에서는 통계적 근사를 버리고 **실제 발생 시각을 보존하는 타임스탬프 슬라이딩 윈도우(대안 D)**가 유일하게 정확성을 보장하는 정답입니다. 또한 폐루프 인프라 차단 구조와 결합하여 리소스 비대화 없이 완벽한 저지연 및 정확도를 달성했습니다.
