## 1. 배경 및 문제 제기

### 1.1 CI 실패 현상 (Issue & Incident)
- 커밋 `280a020` main push CI 실행 중 `tests/unit/test_auth_window.py::test_concurrent_record_failure_race_condition`에서 `AssertionError: assert 4 == 5` 간헐적 실패 발생.
- 5개 스레드가 동일 파티션 키(`SPRAY#<ip>`)에 동시 인입할 때, 낙관적 동시성 제어(OCC) 재시도 소진으로 1건의 계정 누적이 유실(Lost Update)되어 단언문 실패 발생.

### 1.2 핵심 딜레마
1. **지연시간 예산 (10초 관통 SLA)**: DynamoDB 원자적 집계 및 차단 결정은 전체 파이프라인의 극히 일부(수십 ms 이내)를 소모해야 함.
2. **동시성 충돌 (Race Condition)**: 복수의 Lambda 인스턴스가 단일 IP에 대해 밀리초 단위로 동시 인입될 때 데이터 유실이 발생하지 않아야 함.
3. **탐지 정확도 (Detection Accuracy)**: 5분(300초) 윈도우 경계면 전후로 분할 인입되는 공격 트래픽에 대한 탐지 누락(False Negative)이 없어야 함.

## 2. 아키텍처 대안 3종 설계 및 수학적 모델

### 2.1 대안 A: 단일 키 슬라이딩 윈도우 + OCC (현행 구조 보완)
- **구조**: 단일 파티션 키(`SPRAY#<ip>`), DynamoDB `UpdateItem`의 `ConditionExpression`을 통한 윈도우 만료 판별 및 신규 개설.
- **동시성 모델**: 충돌 발생 시 `ConditionalCheckFailedException`을 캐치하여 최대 $K$회 재시도 (마이크로 지터 5~25ms 적용).
- **수학적 특성**:
  - 윈도우 형태: 완벽한 슬라이딩 윈도우 ($P(\text{Boundary Split}) = 0$).
  - 충돌 확률: 동시 스레드 수 $N$에 비례하여 충돌 확률 $P(\text{Collision})$ 증가.
  - 최악 실패 모드: 재시도 $K$회 소진 시 데이터 유실 (Lost Update).

### 2.2 대안 B: 고정 텀블링 윈도우 (Fixed Tumbling Window)
- **구조**: 시간 버킷 파티션 키(`SPRAY#<ip>#{epoch // 300}`).
- **동시성 모델**: DynamoDB 네이티브 `ADD` 연산자는 아이템 부재 시 자동 생성(Upsert)하므로 조건식(`ConditionExpression`) 제거.
- **수학적 특성**:
  - 충돌 확률: **수학적 0% (충돌 및 재시도 완전 부재, 락 프리)**.
  - 윈도우 형태: 5분 고정 텀블링 윈도우.
  - 최악 실패 모드: **경계면 분할(Boundary Split / Split-Brain Counter)**.
    $$\text{공격이 경계면에 걸칠 확률 } P(\text{Split}) = \frac{T_{\text{attack}}}{300\text{s}}$$
    경계면 통과 시 카운트가 분할되어 실제 임계치(5회) 도달 공격에 대해 최대 $2 \times (\text{threshold} - 1) = 8$회까지 탐지 누락 발생.

### 2.3 대안 C: 가중 슬라이딩 윈도우 (Weighted Two-Bucket Sliding Window)
- **구조**: 시간 버킷 파티션 키(`SPRAY#<ip>#{epoch // 300}`). Cloudflare Rate Limiter 표준 알고리즘 채택.
- **동시성 모델**:
  - **쓰기 (Ingestion)**: 조건식 없는 네이티브 `ADD` 1회 실행 $\rightarrow$ **충돌률 0%, 재시도 0회, 단일 RTT (2~5ms)**.
  - **읽기 / 위협 판정 (Check Threat)**: 현재 버킷($B_c$)과 직전 버킷($B_{p}$)을 조회하여 시간 경과 비율에 따른 가중합 추정:
    $$\text{Estimated Count} = \text{Count}(B_c) + \text{Count}(B_{p}) \times \left(1 - \frac{t_{\text{current}} \bmod 300}{300}\right)$$
- **수학적 특성**:
  - 충돌 확률: **0% (대안 B와 동일한 락 프리 원자성)**.
  - 윈도우 형태: 슬라이딩 윈도우 근사치 (오차율 $\le 5\%$).
  - 최악 실패 모드: 직전 윈도우 내 이벤트 분포의 극단적 편향 시 경미한 추정 오차(소수점 단위).

## 5. 최종 구현 권고안

### 채택: 대안 C (가중 슬라이딩 윈도우) 또는 단기 A 보완 + 중기 C 전환
1. **단기 조치 (즉시 CI 복구)**:
   - `auth_window.py`의 `MAX_OCC_RETRIES`를 5로 상향하고 5~25ms 마이크로 지터를 주입하여 main 브랜치 CI를 즉시 녹색으로 복구.
2. **핵심 엔지니어링 구현 (대안 C 전환)**:
   - 쓰기 시 `ConditionExpression` 제거 및 버킷 키(`SPRAY#<ip>#{epoch // 300}`) 적용으로 쓰기 충돌 원천 제거.
   - `check_threat` 판정 시 직전 버킷과 현재 버킷의 가중합($\ge 4.5$ 이상 시 차단) 적용.
   - 면접 및 포트폴리오에서 **"Cloudflare Rate Limiter 모델을 벤치마킹하여 OCC 경합과 경계면 분할 문제를 동시에 해결한 DevSecOps 성능 최적화 사례"**로 강력한 엔지니어링 근거 확보.
