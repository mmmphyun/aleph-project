## 1. 티켓 본문 반영 범위와 증거 제한

티켓은 SSH·Web 실사건 각 1건 이상의 2차 보고서 전문과 CloudWatch 원문 대조,
보호 필드 무결성, 고정셋 정량 지표, S3 HTML 3개 단락의 2~3문장 품질 검수를 요구한다.
추가 과제는 Nova Micro의 실제 `stopReason` 확인, 로그 보강, 토큰·프롬프트 튜닝,
응답 수용 기준 검토와 실제 `converse` 정상 보강 실증이다.

현재 PC의 기본 Boto3 세션은 프로필 없음·리전 없음·자격증명 없음으로 확인됐다.
AWS·Bedrock·S3·Slack은 호출하지 않았고 인프라도 변경하지 않았다. 아래 수치는 모두
저장된 합성 모델 응답을 주입한 오프라인 회귀다. 이를 실사건 보고서나 실제 모델의
환각 방어율·운영 성공률·Fallback 0% 실적으로 대체하지 않는다.

| 완료 조건 | 이번 증거 | 상태 |

## 2. 증상과 원인 가설을 구분한 검토

티켓의 경고는 `_converse_response_text`의 종료 조건 거부와 부합하지만 실제
`stopReason` 값은 없다. 따라서 **max_tokens가 원인이라고 확정할 수 없다.**
입력 토큰 증가 자체가 출력 상한 도달의 증거도 아니다. 실제 응답의 종료값과
`usage.inputTokens`, `outputTokens`, `totalTokens`를 먼저 대조해야 한다.

또한 [P5-2 10월 30일 검증](../cloud-b/2026-10-30-p5-2-panel-verification.md)은
고정 로그 보조 스크립트 사건 `INC-1793322987-0090`에서 `enhanced=1`을 기록한다.
이는 실제 공격 트래픽 실측이 아니며, 티켓의 이전 회차 Fallback 증상과 동일 입력·배포인지도
미확인이다. 한 건의 성공을 일반 성공률로, 이전 경고를 현재 전 회차 실패로 확대하지 않는다.

운영 경로의 `remediation.llm_worker.execute_bedrock_analysis`는 보안 프롬프트·파서와
`_converse_response_text`를 호출하지만 Converse는 자체 수행한다. 현재 main의 워커는
종료 포장 오류까지 넓은 except에서 `call_failed/bedrock_call`로 집계한다.
반면 보안 어댑터는 이를 `parse_failed/converse_envelope`로 구분한다.
새 `cloudshield.bedrock_response` 진단은 공통 추출 함수에서 발생하므로 두 경로의 종료 사유를
보여준다. 워커의 예외 분류를 고쳤거나 배포 버전과 main이 같다고 주장하지 않는다.

## 3. 보안 도메인 변경과 수용 규격

`build_bedrock_analysis_prompt`는 `summary_ko`, `recommendations` 두 키만 출력하도록
요청한다. 기존 파서가 이미 지원하던 부분 응답 경로를 사용하며, 병합 결과는 전체
`IncidentReport`로 다시 검증한다. 모델이 보호 필드를 생략해도 원본에서 보존하고,
제공한 보호 필드가 다르면 엄격 경로에서 전체 응답을 거부한다. 이전 전체 JSON 응답 호환도 유지한다.

각 분석 단락은 제목·LF 포함 400자, 전체 1200자, 권고 각 500자 상한을 유지한다.
프롬프트와 SSH/Web Few-shot만 단락당 2~3문장으로 바꿨다. 문장 수와 사실성은
운영 파서의 보장으로 표현하지 않는다. 평가셋은 별도 검수하며, 마침표 뒤 공백·종료를
세는 보조 검사는 고정된 평문 예시에만 사용한다.

새 INFO 이벤트는 다음처럼 본문 없이 종료값과 유효한 정수 사용량만 기록한다.

```json
{"event":"cloudshield.bedrock_response","stop_reason":"max_tokens","inputTokens":3000,"outputTokens":2048,"totalTokens":5048}
```

위 숫자는 형식 설명용 예시이며 실측이 아니다. 종료값은 고정 허용 목록만 기록하고,
누락·타입 오류·미지 값은 `unknown`으로 대체한다. 사용량은 bool을 제외한 0~10억 정수만
기록한다. 응답·입력 로그·임의 종료 문자열·SDK 오류 본문은 기록하지 않는다.
사건 결과 지표는 기존 `cloudshield.llm_analysis` 이벤트만 집계한다. 진단 이벤트를
성공/Fallback 분모에 더하지 않으며, 사건 연결은 동일 Lambda 요청 로그와 사건 상태 로그로 대조한다.

| 종료·응답 조건 | 처리 |
| --- | --- |
| end_turn + assistant/text 전용 + 유효한 JSON·3단 규격·보호 필드 | 보강 수용 |
| end_turn이나 JSON·규격·필드 무결성 실패 | 동일 원본 반환 |
| max_tokens, 완전해 보이는 JSON 포함 | 잘림 가능성이 있으므로 원본 유지 |
| stop_sequence | 현재 요청에 stopSequences가 없어 정상 종료로 추정하지 않음 |
| tool_use, 필터·가드레일·미지/누락 종료값, 혼합 도구 블록 | 원본 유지 |
| 예상 SDK·권한·타임아웃 오류 | 보안 어댑터는 원본·고정 상태 기록 |
| 입력 오류·예상 밖 프로그래밍 오류 | 보안 어댑터에서 예외 전파 |

선별 수용 완화는 실제 응답 근거 없이 도입하지 않았다. AWS는 max_tokens를 사용자 또는
모델 출력 상한 도달로 설명한다. stopSequences는 요청에서 지정하는 중단 문자열이다.
[Nova 응답 규격](https://docs.aws.amazon.com/nova/latest/userguide/complete-request-schema-response.html),
[Nova Converse 추론 설정](https://docs.aws.amazon.com/nova/latest/userguide/using-converse-api.html).

보안 어댑터의 출력 예산은 2048→4096토큰으로 늘렸지만, **운영 워커 자체 상수는 여전히
2048**이다. 이 PR만으로 운영 maxTokens가 증가하지 않는다. 클라우드 A는 배포 시 보안
어댑터 재사용 또는 워커 설정 일원화를 검토해야 한다. 코드·IaC·실배포는 A 소유 영역이다.
SDK 연결/읽기 2/20초·시도 1회·입력 50줄/32KiB·응답 32KiB 제한은 유지했다.

## 5. 합성 SSH·Web 전문과 근거 대조표

이 절의 두 전문은 **사전 작성한 합성 기대 응답**이다. Nova Micro 생성 결과·실사건
보고서·S3 업로드 산출물이 아니다. 원문 5줄과 1차 모델·응답 포장은 고정셋의 `ssh-0`,
`web-0`에 전문을 보존한다. 실제 사건이 확보되면 별도 증거로 추가하고 이 합성 표본과 구분한다.

### 합성 SSH: P5-3-SYNTHETIC-SSH-0

```text
[1. 침해 개요]
출발지 IP 198.51.100.50의 SSH 인증 실패가 반복됐습니다. 제공된 표본은 단일 계정을 대상으로 합니다.

[2. 관측 로그 근거]
Oct 30 08:00:01부터 Oct 30 08:00:05까지 audit_0 계정의 Failed password가 5건 관측됐습니다. 성공 인증 로그는 제공되지 않았습니다.

[3. 영향도 및 침해 판정]
침해 성공과 실제 격리 결과는 미확인입니다. 영향 범위는 제공된 실패 표본으로 한정하며 원본 매퍼 판정을 유지합니다.

[즉시 조치] audit_0의 실패 시각 인접 성공 인증과 세션 로그를 대조
[설정 점검] TCP 차단·EC2 격리 집행 근거와 정상 관리자 접속 영향을 확인
[재발 방지] 비밀번호 인증 정책을 검토하고 승인된 재검증 후 재발 여부를 관측
```

### 합성 Web: P5-3-SYNTHETIC-WEB-0

```text
[1. 침해 개요]
출발지 IP 198.51.100.50의 Web 경로 열거가 관측됐습니다. 표본은 서로 다른 경로 5개입니다.

[2. 관측 로그 근거]
30/Oct/2026:08:01:01의 /admin 응답은 401이며 /backup·/config는 404·403입니다. /debug·/metrics는 200으로 응답했습니다.

[3. 영향도 및 침해 판정]
HTTP 200만으로 민감 정보 노출을 확정할 수 없습니다. HTTP 403만으로 WAF 차단을 단정할 수 없어 응답 본문과 WAF 집행 근거를 추가 확인해야 합니다.

[즉시 조치] URI·시각·출발지 IP를 WAF ALLOW/BLOCK 원문과 대조
[설정 점검] /debug·/metrics 응답 본문과 접근 정책·정상 사용자 영향을 확인
[재발 방지] 불필요한 진단 경로를 정리하고 승인된 재점검으로 노출 여부를 확인
```

## 6. 실인프라 검수를 끝내기 위한 증거와 A 연계

아래 자료가 있어야 실제 DoD를 판정할 수 있다. 자격증명 값은 문서·이슈에 넣지 않는다.

   CloudWatch log group/stream·eventId·timestamp가 있는 원문, 실제 공격/보조 주입 구분.
2. 같은 사건의 1차 IncidentReport, 2차 전체 IncidentReport, 실제 Converse 원본 응답
   (stopReason·usage 포함), 모델 ID와 배포 버전. 보호 필드와 사실 근거를 1:1 대조한다.

   실제 화면에서 3단 문장·원문·권고의 손실과 잘림을 확인한다.
4. 동일 고정 입력·모델·설정의 변경 전후 실행 결과. 정상/Fallback 집계는 사건별로
   중복/재시도를 구분하며, 분모와 관측 기간을 적는다. 표본 부족은 미측정으로 표시한다.
5. 클라우드 A가 운영 워커의 토큰 예산·예외 분류와 배포 아티팩트를 정합화한 뒤
   실제 converse 및 S3 결과를 확보한다. 이 PR은 A 코드를 수정하지 않는다.
