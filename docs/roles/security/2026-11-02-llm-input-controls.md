## 1. 문제와 근거의 범위

기존 빌더는 로그를 JSON 데이터로 구분하고 용량을 제한하지만, JSON을 해석한 모델에는
비표시 제어문자가 원래 값으로 전달될 수 있다. 광범위한 허용 문자 정규식으로 제거하면
퍼센트 인코딩·쿼리·따옴표·공격 문법까지 달라져 사후 분석의 근거를 훼손할 수 있다.

기존 [실측 요약](evidence/p5-3-2026-10-30/user-supplied-bedrock-measurements.json)의
`content_filtered`는 초기 main **Web 대조군**의 사용자 제공 관측이다. 이후 P5-3의 SSH·Web
각 한 건은 정상 분석으로 기록되어 있다. 실패 요청의 전체 입력·배포 리비전·요청 ID가
없으므로 Hydra 단어장·핸드셰이크 오류가 원인이라고 확정하지 않는다. 현재 SSH 생산자는
공격자 IP가 일치하고 `SyslogAuthEvent.parse_line`으로 파싱되는 인증 실패 로그만 전달한다.

이번 변경은 입력 표현을 보강하며 실제 Bedrock의 거부율 감소나 필터 해소를 입증하지 않는다.
모델의 안전 필터나 사용자 설정 Guardrails를 비활성화하지 않는다.

## 2. 전달본에만 적용하는 표현 규칙

`build_bedrock_analysis_prompt`에서 원본 보고서와 로그의 전달 사본만 준비한다.

| 입력 | 전달본 | 보존 대상 |
| --- | --- | --- |
| TAB/LF/CR을 제외한 C0 및 DEL/C1 (`U+0000`~`U+001F`, `U+007F`~`U+009F`) | 문자 그대로의 6자 `\uXXXX` 표기 | 원본 객체·목록은 불변 |
| TAB/LF/CR | 원형 유지 | 로그 배치와 JSON 데이터 경계 |
| 한글·이모지·인쇄 가능한 문자열·기호 | 원형 유지 | IP, 시각, 계정, URI, `%`, `?`, `=`, 따옴표 등 |
| 계정명·요약 등 `base_report` 문자열 | 동일 규칙으로 사본 준비 | 최종 보호 필드는 원본 보고서에서 병합 |

가시화된 제어문자와 원래 문자 그대로의 `\uXXXX`를 포함한 문자열은 같아 보일 수 있다.
따라서 무손실 역변환을 주장하지 않고 원본을 증거로 보존한다. 변환은 전달본의 표현 정책이며
인쇄 가능한 인젝션 문구나 악성 명령을 제거했다는 의미가 아니다. 기존 응답 검증기가
계약 외 필드와 보호 필드 변조를 거부하고, 필터링·중단 응답을 성공으로 승격하지 않는다.

`sanitization` 메타데이터에는 정책 버전, 실제 포함된 로그의 변환 문자·줄 수,
보고서 사본의 변경 여부만 넣는다. 로그 본문에 변환 안내 문구를 덧붙이지 않는다.
프롬프트에는 CloudWatch 감사 자료의 방어 분석 목적과 데이터 내부 지시를 따르지 않을 것을
명시한다. 이는 기존 user 메시지에 포함된 분석 지시이며 새 system 메시지나 필터 설정이 아니다.

## 3. 물리적 제약과 기존 인터페이스

1. 상태성: 순수 변환만 수행하며 호출 간 공유 상태·새 저장소를 추가하지 않는다.
2. 용량: 첫 50줄·원본 줄당 첫 4,096자만 검사하고 **가시화 후에도** 줄당 4,096자·총 32KiB를
   적용한다. UTF-8 문자와 6자 제어문자 표기를 중간 절단하지 않는다. 보고서는 변환 전후
   16KiB, 전체 프롬프트는 JSON 이스케이프 후 256KiB 제한을 유지한다.
3. 일관성: 저장소 접근·새 쓰기 후 읽기가 없어 기존 읽기 일관성 모델을 변경하지 않는다.
4. 순서: 선행 로그 우선 선택·입력 순서를 유지하며 탐지 윈도우와 이벤트 시각을 바꾸지 않는다.
5. 장애: 보안 어댑터는 잘못된 Unicode·입력 타입·용량 초과를 API 호출 전에 전파한다.
   예상 SDK 장애·중단 응답은 기존처럼 원본 보고서로 복귀한다. 플랫폼의 별도 예외 정책은
   변경하지 않는다.

클라우드 A의 `execute_bedrock_analysis`가 같은 빌더를 호출하므로 플랫폼 코드 수정 없이
전달본에 반영된다. 워커가 HTML 렌더러에 넘기는 `raw_logs`는 원본 그대로다. 공통 계약,
탐지·차단 판단, 출력 2,048토큰·타임아웃·시도 횟수, S3·Slack·배포 설정은 변경하지 않는다.

## 4. 검증 및 배포 구분

- 기존 테스트를 유지하고 모든 대상 C0/C1 문자, 정상 기호·UTF-8·줄바꿈 보존,
  보고서 문자열의 우회 재유입, 최종 보호 필드 불변을 검증한다.
- 가시화 팽창 후 줄·바이트 상한과 6자 표기의 원자적 절단, 보고서 팽창 시 API 호출 전 거부를
  검증한다. 원본 줄 선택·입력 오류·JSON 이스케이프 상한 회귀도 유지한다.
- 실제 플랫폼 워커 함수에 합성 Converse 응답을 주입하여 정상 보강과 `content_filtered`,
  `guardrail_intervened`의 원본 복귀, 원본 로그 HTML 소비를 검증한다.
- 검증 명령: `.venv/Scripts/python.exe -m pytest tests/unit/test_llm_analyzer.py -q`,
  LLM 집중 테스트 **280건 통과**. 필수 전체 게이트 `powershell .\scripts\check.ps1`은
  **1,630 passed, 기존 4 skipped, 기존 경고 1건**, 262.70초, 종료 코드 0이다.
  R&R 3개 파일, 테스트 경로, Ruff lint 및 Python 172개 파일의 format 검사를 통과했다.
  새 회귀는 75건이며 새 skip은 없다. 경고는 기존 smoke 테스트의 DNS 소켓 차단이다.
- Windows 검증 환경은 `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`로 부모·자식 Python의
  인코딩을 일치시킨다. 첫 전체 실행은 기존 패키징 테스트의 CP949/UTF-8 출력 디코딩
  불일치로 실패했다. 해당 테스트는 환경을 통일한 재검증에서 통과했으며 검증 코드는
  수정하지 않았다. 실행 정책 우회나 테스트 제외 옵션은 사용하지 않는다.
- AWS·Bedrock·Slack 실호출이나 재배포는 수행하지 않는다. 배포 이후 실제 실패 입력을 보존한
  대조 실측과 근거 검수는 별도 협업 범위이며, 로컬 합성 테스트를 운영 성공률로 확대하지 않는다.
