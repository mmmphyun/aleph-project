01. PROBLEM DEFINITION

사람이 직접 대응하면 공격을 제때 막기 어렵습니다

수동 보안 관제의 대응 지연 문제를 해결하고자 합니다.

핵심 문제 상황

사람이 경보를 확인하고 차단하는 동안에도 공격은 계속 진행됩니다.

수동 대응의 지연

알림 확인부터 콘솔 접속까지 지연이 발생해 대응 골든타임을 놓치기 쉽습니다.

단일 계층의 한계

네트워크 방화벽만 막으면 웹 브라우저의 기존 연결과 세션 침투 위험이 남습니다.

차단 코어 검증 집중

관제 화면 개발보다 실제 인프라를 신속하게 격리하는 차단 엔진에 집중했습니다.

해결 방향: 공격 로그를 감지해 10초 안에 자동 차단과 알림까지 연결한다.
1. 본 프로젝트에서 정의한 핵심 문제는 "탐지 후 사람이 대응하는 동안 공격이 계속될 수 있다"는 점입니다. 2. 담당자가 알림을 확인하고 IP를 차단하기 전까지 공격이 이어져 계정이 탈취될 위험이 있습니다. 3. 따라서 화면 개발에 치우치지 않고, 공격 발생 즉시 사람이 콘솔을 조작하지 않아도 10초 이내에 자동 차단과 알림을 완결하는 파이프라인을 구축하는 데 집중했습니다.
02. CORE METRICS

10초 대응 목표와 진행 상황

10초는 달성 결과가 아니라 실제 AWS 환경에서 검증할 핵심 목표입니다.

≤ 10초 대응 시간 목표
0건 수동 개입 목표
10초 측정 기준: 로그 기록부터 필요한 차단 API 성공 및 Slack Webhook 성공 응답까지

SSH 탐지·차단 로직

목 데이터 기반 무차별 대입 및 스프레이 판정·차단 로직 구축

2. 가상 환경 검증
가상 환경 자동화 테스트 통과

가상 AWS(moto) 환경에서 자동화 단위·통합 테스트 통과 (인프라 미배포)

3. 실 AWS 배포·실측 (예정)
인프라 배포 및 10초 실측

Phase 3~4에서 Terraform 배포 후 실제 클라우드 인프라를 대상으로 10초 검증 예정

1. CloudShield가 추구하는 핵심 지표는 "10초 이내 무인 자동 대응"과 "수동 개입 0건"입니다. 2. 10초의 측정 기준은 타깃 EC2 서버에 공격 로그가 기록된 시각부터 해당 공격에 필요한 차단 API가 성공하고 Slack Webhook 성공 응답을 수신하기까지의 시각입니다. 3. 10초는 이미 달성한 결과가 아니라 9주차 Phase 4에서 실제 AWS 인프라를 대상으로 검증할 목표입니다. 4. 현재 실제 AWS 미배포 상태로, 목 데이터와 가상 AWS(moto) 환경에서 SSH 무차별 대입 및 스프레이 파이프라인 단위·통합 테스트를 통과했습니다.

실시간 핵심 대응 경로 (≤ 10초 목표 • LLM 배제) 단일 스트림 • 이벤트 구동

05 • 상황 전파

차단 완료 ┄┄→ 비동기 LLM 사후 분석 (Out-of-band • 연동 예정 • 10초 실시간 경로 제외)
자동 실행 없음 • 리포팅 전담
• 사건 심층 요약: 차단 완료 후 침해 정황 및 로그 맥락을 종합 분석하여 보고서 생성
• 재발 방지 권고안: 취약 계정 정책 강화 및 사후 조치 가이드를 제시 (자동 차단/실행 미수행)
AWS 서비스 (배포 예정)

EC2(로그 발생 서버) • CloudWatch Logs(수집) • Lambda(컴퓨팅) • DynamoDB(상태 DB) • SG/WAFv2(접근 제어)

Python 코어 • 검증 도구

Python(탐지/오케스트레이션) • Boto3(AWS SDK) • Pydantic(데이터 계약 검증) • Moto 기반 AWS 호출 모의 테스트

인프라 코드 • 외부 연동

Terraform/HCL(AWS Provider 배포 예정) • Slack(외부 협업 API 알림) • LLM 사후 분석(연동 예정)

1. CloudShield 아키텍처는 10초 이내 무인 차단을 위한 실시간 핵심 경로와 심층 분석을 위한 비동기 LLM 사후 분석 경로를 철저히 분리했습니다. 2. 실시간 핵심 경로는 'EC2 로그인 실패 로그 발생 → CloudWatch Logs 수집 → Lambda 탐지 및 DynamoDB 300초 상태 누적 → Boto3 기반 L4 SG 격리 및 L7 WAF 차단 → Slack 알림 전파'의 단일 스트림으로 동작하며, 10초 목표 달성을 위해 지연 요인인 LLM 호출을 일체 배제했습니다. 3. 차단 완료 후 실행되는 비동기 사후 분석 경로는 LLM을 연계하여 침해 정황을 심층 요약하고 재발 방지 권고안을 제시하는 Out-of-band 리포팅 파이프라인으로 설계되었으며, 자동 차단이나 API 실행 권한은 없습니다. 4. 기술 스택 소속과 관련하여 EC2, CloudWatch, Lambda, DynamoDB, WAF는 AWS 서비스(배포 예정)이며, Boto3는 AWS SDK, Pydantic은 계약 검증 라이브러리, Moto는 AWS 호출 모의 테스트 도구입니다. 인프라는 향후 Terraform(HCL)으로 배포할 계획입니다. 5. CloudTrail은 5~15분의 전달 지연으로 실시간 경로에서 배제했으며, 현재는 실제 AWS 미배포 상태로 moto 가상 환경에서 코어 파이프라인 무결성을 검증한 상태입니다.

보안(탐지), Cloud A(차단), Cloud B(수집·알림)의 책임을 명확히 구분합니다.

05. STAGE 1 : SIMULATION

정상 접속과 공격 로그 비교

실제 침해와 동일한 패턴을 모의 재현하여 탐지 규칙을 검증합니다.

정상 사용자 접속 단일 세션 통과

공개키 인증 1회 성공 후 즉시 연결

Accepted publickey for ubuntu from 203.0.113.10 port 52310 ssh2
공격 시도 (Hydra) 연속 실패

짧은 시간 동안 동일 IP·계정으로 인증 실패 반복

Failed password for root from 198.51.100.20 port 45210 ssh2
Failed password for root from 198.51.100.20 port 45212 ssh2
Failed password for root from 198.51.100.20 port 45214 ssh2
다음 단계 질문: 반복 실패와 계정 분산 시도를 어떻게 구분할까?
1. 모의 공격 시나리오는 격리된 환경에서 Hydra를 통해 타깃 인스턴스에 SSH 인증 실패를 발생시킵니다. 2. 정상 접속은 공개키 1회로 통과하지만, 공격은 짧은 시간 안에 수많은 실패 로그(Failed password)를 남깁니다. 3. 단순 오타와 실제 공격, 그리고 단일 계정 집중 공격과 다수 계정 분산 공격을 구분하는 기준이 다음 장의 위협 탐지 룰입니다.
06. STAGE 2 : INGESTION

로그 수집: 서버에서 람다까지 최단 경로 연결

로그가 서버에 머무는 시간을 줄이기 위해 전송 대기 시간을 2초로 단축했습니다.

STEP 1
서버 로그 기록

EC2 auth.log에 로그인 실패 이벤트 즉시 기록

STEP 2
짧은 전송 대기

CloudWatch Agent 2초 플러시 설정 반영 (force_flush: 2s)

STEP 3
탐지 함수 호출

CloudWatch Logs 구독 필터 매칭 즉시 Lambda 실행

Cloud B 담당 영역

CloudWatch Agent 구성에 2초 플러시 설정을 반영하여 로그 체류 시간 단축을 도모합니다.

전송 지연 실측 예정

2초 플러시 설정 외 네트워크 지연을 포함한 전체 수집 시간은 Phase 4 실제 AWS 환경에서 실측합니다.

1. 2구간 수집의 흐름은 'EC2 로그 → CloudWatch Agent(2초 플러시 설정) → CloudWatch Logs 구독 필터 → Lambda'의 경로입니다. 2. CloudWatch Agent 설정에 force_flush_interval 2초를 반영했습니다. 3. 이 설정값 반영만으로 전체 10초 완결이 입증된 것은 아니며, 실제 CloudWatch Logs 전달 지연과 종단 간 시간은 Phase 4 실제 AWS 배포 후 실측 검증할 예정입니다.
07. STAGE 3 : DETECTION

위협 탐지: 최근 5분 기준 공격 판정

오탐을 줄이고 침해를 포착하기 위해 최근 5분(300초) 누적 기록을 평가합니다.

공격 유형 판정 기준 (최근 5분) 대응 조치
무차별 대입 SSH_BRUTE_FORCE (HIGH) 같은 IP와 같은 계정 조합에서 최근 5분 내 실패 5회 이상 (우선 판정) L4 SG 격리 + L7 WAF 차단 (구현 완료)
패스워드 스프레이 SSH_PASSWORD_SPRAYING (MEDIUM) 같은 IP에서 최근 5분 내 서로 다른 계정 2개 이상으로 실패 L7 WAF 차단 (구현 완료)
기준 미충족 미달 이벤트 탐지 임계치(5회 또는 2개 계정) 미달 자동 차단하지 않음
판정 원칙: 두 기준이 동시에 맞으면 무차별 대입 판정을 우선합니다. 무차별 대입 • 스프레이 룰 구현 완료
1. 위협 탐지 단계에서는 최근 5분(300초) 동안의 로그인 실패 기록을 집계해 공격 여부를 엄격하게 판정합니다. 2. 무차별 대입: 같은 IP와 같은 계정 조합에서 최근 5분 내 5회 이상 실패 시 HIGH 위험도로 L4 SG 격리와 L7 WAF 차단을 동시 집행합니다. 3. 패스워드 스프레이: 같은 IP에서 최근 5분 내 서로 다른 계정 2개 이상으로 실패 시 MEDIUM 위험도로 L7 WAF 차단을 단독 집행합니다. 4. 두 기준이 동시에 성립하면 무차별 대입을 우선 판정하며, 탐지 임계치에 미달한 이벤트는 자동 차단하지 않습니다. 5. DynamoDB 직전·현재·직후 3-버킷 조회 후 타임스탬프를 실제 300초 윈도우로 필터링하여 버킷 경계면 누락과 동시성 경합을 안전하게 방어합니다.
08. STAGE 4 : REMEDIATION

계층별 차단과 관제 알림

Cloud A는 차단 집행을, Cloud B는 Slack 상황 전파를 전담합니다.

무차별 대입 대응 • 구현 완료
L4 SG 격리 + L7 WAF 차단 (Cloud A)
네트워크 방화벽(보안그룹) 격리:

인/아웃바운드가 전면 차단된 격리 보안그룹으로 교체해 신규 접속을 끊습니다.

웹 방화벽(WAF) 차단:

공격자 IP(/32)를 WAF IPSet에 등록해 인프라 전체의 웹 접근을 함께 봉쇄합니다.

스프레이 • 웹 스캔 대응
L7 WAF 웹 방화벽 단독 차단 (Cloud A)
패스워드 스프레이 (구현 완료):

서버 전체를 격리하지 않고 공격자 IP만 WAF IPSet에 등록해 웹 요청을 단독 차단합니다.

웹 탐색 스캔 확장 (Phase 2.5 예정):

비정상 URL 경로 탐색 시 WAF 단독 차단 규칙을 적용하며, Cloud B 알림으로 연계됩니다.

결함 영향도: Slack 알림 전송이 실패해도 이미 적용된 L4·L7 차단 API 호출은 취소되지 않고 유지됩니다. 10초 대응 실측 예정 (Phase 4)
1. Cloud A 차단 엔진은 공격 유형에 따라 계층을 분리해 적용합니다. 2. SSH 무차별 대입은 L4 SG 격리와 L7 WAF 차단을 동시에 집행합니다. 3. 패스워드 스프레이는 구현 완료된 기능으로, 서버 전체를 격리하지 않고 L7 WAF 차단만 단독 적용합니다. 4. 웹 탐색 스캔 대응은 Phase 2.5 확장 예정입니다. 5. Cloud B의 Slack Webhook 전송에 실패하더라도 이미 완료된 Boto3 차단 API 호출 결과는 롤백되지 않고 유지되도록 설계했습니다.
09. RECOVERY & ROLLBACK

오탐 복구: 정상 이용자 복구 절차

잘못 차단된 정상 서비스 트래픽을 신속히 되돌리기 위한 2단계 복구 절차를 설계했습니다.

1단계
네트워크 차단 원복 (설계)

격리 시 보존한 원본 보안그룹 목록을 역참조하여 재할당하는 롤백 절차를 설계했습니다.

• 현재 코드 미구현 상태이며 차기 마일스톤 구현 과제입니다.
2단계
WAF 차단 목록에서 오탐 IP 제거 (설계)

전체 차단 목록을 유지한 채 오탐된 IP 주소만 선별하여 IPSet에서 삭제하는 절차를 설계했습니다.

• LockToken 기반 낙관적 락으로 동시 수정을 방어하도록 설계했습니다.
진행 상태: 복구 절차 설계 완료 (코드 미구현) • Phase 4 구현 및 실환경 검증 예정 검증 예정 (Phase 4)
1. 오탐 발생 시의 복구 절차는 네트워크 원복과 WAF IP 제거의 2단계 아키텍처로 설계했습니다. 2. 네트워크 원복은 격리 전 원본 보안그룹을 보존해 재할당하고, WAF 원복은 LockToken 기반으로 오탐 IP만 선별 삭제하는 구조입니다. 3. 현재 복구 기능은 코드로 구현된 상태가 아니며, 아키텍처 문서상에 절차 설계가 정리된 단계입니다. 4. 복구 코드 구현 및 실제 AWS 환경에서의 동작 검증은 Phase 4에서 진행할 계획입니다.
