# SentinelHub 프로젝트 상세 계획

## 1. 문서 목적

이 문서는 프로젝트를 시작하기 전에 팀이 같은 방향으로 움직이기 위한 실행 계획입니다.

프로젝트의 목표는 멀티 계정 AWS 환경에서 발생하는 위험한 접근과 변경을 탐지하고, 세 가지 시나리오를 목업으로 검증한 뒤 선정한 하나의 대표 시나리오에서 승인 기반 자동 대응을 수행하는 것입니다.

이 문서는 다음을 결정합니다.

- 무엇을 만들 것인가
- 무엇을 만들지 않을 것인가
- 누가 어떤 영역을 맡는가
- 과목을 아직 배우지 않았을 때 어떻게 개발을 이어갈 것인가
- LLM을 어떤 방식으로 사용할 것인가
- 어떤 조건을 만족해야 기능이 완료되는가
- 레드팀은 무엇을 검증할 것인가

## 2. 프로젝트 한 줄 정의

> 멀티 계정 AWS 환경에서 세 가지 보안 시나리오를 공통 흐름으로 목업 검증하고, 그중 선정한 하나의 대표 시나리오를 테스트 AWS 환경에서 자동 대응까지 검증하는 클라우드 보안 운영 플랫폼

## 3. 공통 사용자 흐름

대표 시나리오가 확정되기 전에는 다음 공통 흐름을 세 시나리오에 적용합니다.

1. 테스트 이벤트 또는 AWS 이벤트가 수집됩니다.
2. 이벤트는 공통 스키마로 정규화됩니다.
3. 결정론적 규칙으로 위험도가 평가됩니다.
4. 승인 요청 또는 대응 결정이 생성됩니다.
5. 목업 흐름에서는 대응 결과를 기록하고, 대표 시나리오에서는 실제 AWS 자동 대응을 실행합니다.
6. 실행 전후 상태와 담당자 행동이 감사 로그에 남습니다.
7. 대표 대응이 JIT 권한이면 Session Policy와 TTL 만료를, 보안 설정 변경이면 원복 결과를 검증합니다.

## 4. 범위

### 4.1 반드시 구현할 범위

- 관리·보안·업무 계정으로 구성된 AWS 3계정 구조
- Terraform으로 재현 가능한 기본 인프라
- VPC, 서브넷, 라우팅, 보안 그룹
- 개발자·보안 담당자·관리자 역할 구분
- 승인 인터페이스와 대응 결과 기록
- CLI 또는 간단한 웹 기반 승인 인터페이스
- CloudTrail API 이벤트·AWS Config 이벤트·표준화된 테스트 이벤트 수집
- 비식별화한 CloudTrail Fixture 3종과 파서 테스트
- 위험도 분류 규칙
- 세 시나리오의 목업 탐지·승인·대응 결과 흐름
- 선정한 대표 시나리오의 실제 AWS 자동 대응 플레이북 1개
- 감사 로그
- 레드팀 공격 시나리오 3개
- LLM 기반 사건 요약과 대응 추천

### 4.2 후순위 범위

- 실제 GuardDuty 결과 연동
- VPC Flow Logs 연동
- IAM Access Analyzer 연동
- 간단한 운영 대시보드
- Slack·Discord Interactive Approval adapter
- AWS Config 직접 연동
- 개인별 Ephemeral Role
- 비용 현황 표시
- 대표 시나리오 확정 전까지 특정 실제 대응 방식(JIT 발급, 권한 제한, 보안 그룹 원복 등)을 필수로 고정하지 않음

### 4.3 제외할 범위

- 자체 SIEM 구축
- 자체 머신러닝 모델 학습
- 여러 클라우드 동시 지원
- Kubernetes 보안
- 운영 계정에 대한 무승인 자동 변경
- 실제 공격 대상에 대한 침투 테스트
- 복잡한 사내 IdP 또는 상용 IAM 제품 구현
- NACL 기반 C2 IP 자동 차단

대표 시나리오는 안전성, 원복 가능성, 데모 재현성, 팀원 역할 기여도, 구현 난이도를 기준으로 추후 선정합니다. 대표 시나리오가 확정되기 전에는 세 시나리오 모두 목업 경로를 유지합니다. 범위를 추가하려면 기존 필수 시나리오를 훼손하지 않는지 먼저 확인하고, 팀 전체의 합의를 PR 또는 ADR로 남깁니다.

## 5. 목표 아키텍처

```text
┌──────────────────┐
│ 관리 계정         │
│ Organizations     │
│ 공통 정책·계정관리 │
└────────┬─────────┘
         │
┌────────▼─────────┐       ┌──────────────────┐
│ 보안 계정         │       │ 업무 계정         │
│ EventBridge       │◄──────│ CloudTrail API   │
│ S3 CloudTrail     │◄── 감사│ IAM·S3·VPC      │
│ GuardDuty/Config  │       └──────────────────┘
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 이벤트 표준화     │
│ 위험도 판단       │
│ 승인 정책         │
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 승인 인터페이스    │
│ 목업 대응 흐름     │
│ 대표 실제 대응     │
│ JIT 또는 원복 검증  │
│ 감사 로그·보고서    │
└──────────────────┘
```

EventBridge 경로는 near real-time 처리를 목표로 하지만 best effort이며, CloudTrail S3 전달은 감사·장기 보관용으로 사용합니다. 프로젝트는 “수초 내 대응”을 보장하지 않고 이벤트 발생부터 대응 완료까지의 실제 지연을 측정합니다.

## 6. 공통 이벤트 계약

아직 GuardDuty나 SOAR를 배우지 않았더라도 모든 기능은 [공통 이벤트 형식](event-schema.md)으로 연결합니다. 수집·정규화와 위험도 평가를 분리하고, 실제 AWS 연동 전에는 Mock 이벤트와 비식별화한 CloudTrail Fixture를 사용합니다.

원칙:

- 이벤트 생성자는 원본 이벤트를 `raw_event`에 보존합니다.
- 이후 모듈은 공통 필드만 사용합니다.
- 실제 AWS 연동 전에는 Mock 이벤트를 사용합니다.
- 실제 연동으로 바꾸더라도 입력·출력 계약은 유지합니다.

## 8. 팀 분업

각 업무는 담당자·리뷰어·백업 담당자를 함께 지정합니다. 담당자가 혼자만 이해하는 구조를 만들지 않는 것이 목표입니다.

### 클라우드 담당

- AWS 계정 구조
- Terraform
- 공통 VPC와 배포
- 계정 간 이벤트 전달
- 비용과 운영 문서

### 보안 담당 A: IAM·접근 통제

- 역할과 최소권한 정책
- JIT 권한 요청·승인·Session Policy·TTL 만료
- 계정 간 AssumeRole
- 위험한 정책 검사

### 보안 담당 B: 탐지·대응

- 이벤트 정규화
- 탐지 규칙
- SOAR 플레이북
- 감사 로그와 사건 보고서

### 네트워크 담당

- VPC·서브넷·라우팅
- 보안 그룹
- VPC Flow Logs
- 네트워크 노출 시나리오

## 9. 개발 순서

### 단계 0: 공통 기반

- 저장소 생성
- 브랜치와 PR 규칙 적용
- Python 버전 고정
- Ruff·pytest·pre-commit 설정
- 이벤트 계약 작성
- 세 가지 시나리오 초안과 목업 이벤트 작성
- Mock 이벤트 생성

완료 기준: 실제 AWS 서비스 없이도 세 시나리오가 이벤트부터 보고서까지 각각 한 번 실행됩니다.

### 단계 1: 최소 수직 흐름

```text
세 가지 Mock 이벤트
→ 공통 이벤트 형식 변환
→ 룰 기반 위험도 판정
→ 승인 또는 대응 결정
→ Mock 대응 결과 기록
→ 보고서 생성
```

완료 기준: 세 시나리오의 목업 흐름이 팀원 누구의 컴퓨터에서도 실행됩니다.

### 단계 2: 대표 시나리오 선정과 실제 연결

- Terraform으로 테스트 계정 인프라 구성
- 안전성·원복 가능성·재현성·팀 기여도를 기준으로 대표 시나리오 1개 선정
- 선정한 시나리오에만 실제 AWS 역할·정책·리소스 변경을 연결
- 실제 대응 결과와 CloudTrail 기록 확인

완료 기준: 선정한 대표 시나리오에서 화면 상태와 AWS 실제 상태가 일치하고, 실행 전후와 원복 또는 TTL 만료 결과가 검증됩니다.

### 단계 3: 탐지와 네트워크 연결

- CloudTrail API 이벤트 또는 AWS Config 이벤트 연결
- IAM 권한 상승 탐지
- 비정상 역할 전환 탐지
- 보안 그룹 노출 탐지
- Flow Logs 연결
- 이벤트 수신 지연 측정

완료 기준: 준비한 공격 이벤트가 사건으로 묶이고, 탐지 근거가 남습니다.

### 단계 4: 대응 고도화와 LLM

- 세 시나리오의 목업 대응 결과 정리
- 선정한 대표 시나리오의 실제 AWS 대응 플레이북 1개 구현
- CLI 또는 간단한 웹 승인 게이트 추가
- AssumeRole Session Policy로 영구 백도어 생성 권한 제한
- 사건 요약과 위험 설명 생성
- 대응 보고서 생성
- 실패·오탐 처리

완료 기준: LLM이 잘못 판단해도 규칙과 승인 절차가 위험한 실행을 막습니다.

### 단계 5: 레드팀과 발표 준비

- RT-01, RT-02, RT-03 실행
- 탐지율과 대응 시간 측정
- 실패한 규칙 수정
- 데모 환경 초기화 절차 작성
- 발표 시나리오와 포트폴리오 자료 정리

## 10. 협업 방식

```text
Issue 생성
→ 브랜치 생성
→ 작은 작업 수행
→ 테스트 실행
→ PR 생성
→ 리뷰 1명 이상
→ CI 통과
→ main 병합
```

하나의 PR은 하루 안에 리뷰할 수 있는 크기로 제한합니다.

좋은 작업 단위:

- IAM 이벤트를 공통 형식으로 변환
- 대표 시나리오 또는 목업 시나리오의 대응 요청 저장
- 만료된 권한의 TTL 처리
- 특정 탐지 규칙 추가
- 특정 플레이북 추가

나쁜 작업 단위:

- 전체 보안 플랫폼 구현
- 여러 기능을 한 PR에 통합
- 테스트 없이 대규모 리팩터링

### Definition of Done

- 담당자가 아닌 사람이 실행할 수 있습니다.
- 입력과 출력이 문서화되어 있습니다.
- 정상 케이스 테스트가 있습니다.
- 실패 케이스 테스트가 있습니다.
- 로그가 남습니다.
- 실제 AWS 변경이 있다면 결과를 확인했습니다.
- 보안 영향이 PR에 기록되어 있습니다.
- 관련 문서가 업데이트되어 있습니다.

## 11. LLM 사용 규칙

모든 팀원이 서로 다른 LLM과 에이전트를 사용해도 다음 기준은 지킵니다.

- 작업 전 저장소 문서와 관련 코드를 읽습니다.
- Issue 범위를 벗어나지 않습니다.
- 기존 인터페이스를 먼저 확인합니다.
- LLM 생성 코드를 그대로 신뢰하지 않습니다.
- 보안 권한과 외부 API 호출을 사람이 검토합니다.
- 테스트를 실행하고 결과를 PR에 남깁니다.
- LLM 사용 범위를 PR에 기록합니다.
- 담당자는 제출한 코드를 설명할 수 있어야 합니다.

LLM은 코드 생성, 테스트 작성, 로그 요약, 문서 초안에 활용합니다. 권한 부여·차단 같은 실제 보안 조치는 결정적 규칙과 승인 게이트가 담당합니다.

## 12. 레드팀 검증

### RT-01: 탈취된 개발자 계정

```text
비정상 로그인
→ 운영 계정 AssumeRole
→ 민감한 S3 접근
→ 탐지·보류·TTL 만료 또는 역할 세션 긴급 무효화
```

### RT-02: IAM 권한 상승

```text
일반 역할
→ PassRole 또는 위험한 AssumeRole
→ 관리자 권한 획득 시도
→ Session Policy와 정책 검사로 영구 백도어 생성 차단
```

### RT-03: 네트워크 노출

```text
위험한 보안 그룹 규칙
→ 테스트 포트 접근
→ Flow Logs 또는 GuardDuty 확인
→ 보안 그룹 규칙 원복
```

모든 테스트는 별도 계정, 더미 리소스, 비파괴적인 API 호출로 제한합니다. 실제 CloudTrail Fixture는 비식별화한 테스트 계정 로그 또는 공식 예시를 사용합니다.

측정할 지표:

- 탐지율
- 평균 탐지 시간
- 평균 대응 시간
- 임시 권한 TTL 만료 성공률
- 긴급 무효화 범위와 소요 시간
- 오탐률
- 감사 로그 누락률
- 이벤트 수신 지연 시간

## 13. 포트폴리오 산출물

- 전체 아키텍처 다이어그램
- Terraform 저장소와 실행 방법
- IAM 권한 설계표
- 이벤트 계약 문서
- 공격·탐지·대응 매핑표
- PR과 코드 리뷰 기록
- CI 실행 결과
- 시나리오별 실행 영상
- 탐지·대응 측정 지표
