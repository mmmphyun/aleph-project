# SentinelHub 프로젝트 상세 계획

## 1. 문서 목적

이 문서는 프로젝트를 시작하기 전에 팀이 같은 방향으로 움직이기 위한 실행 계획입니다.

프로젝트의 목표는 멀티 계정 AWS 환경에서 발생하는 위험한 접근을 탐지하고, 필요한 경우 승인 기반의 임시 권한과 자동 대응으로 피해를 줄이는 것입니다.

이 문서는 다음을 결정합니다.

- 무엇을 만들 것인가
- 무엇을 만들지 않을 것인가
- 누가 어떤 영역을 맡는가
- 과목을 아직 배우지 않았을 때 어떻게 개발을 이어갈 것인가
- LLM을 어떤 방식으로 사용할 것인가
- 어떤 조건을 만족해야 기능이 완료되는가
- 레드팀은 무엇을 검증할 것인가

## 2. 프로젝트 한 줄 정의

> 멀티 계정 AWS 환경에서 비정상적인 권한 사용과 네트워크 노출을 탐지하고, 승인 기반 JIT 권한 및 자동 대응 플레이북으로 처리하는 클라우드 보안 운영 플랫폼

## 3. 최종 사용자 시나리오

개발자가 운영 환경을 점검해야 한다고 가정합니다.

1. 개발자는 운영 계정의 읽기 권한을 요청합니다.
2. 요청에는 작업 목적, 대상 리소스, 필요한 시간, 작업 번호가 포함됩니다.
3. 승인자는 요청 내용을 확인합니다.
4. 승인되면 제한된 시간 동안만 임시 권한이 발급됩니다.
5. 모든 권한 사용 내역은 CloudTrail에 기록됩니다.
6. 시간이 지나면 권한이 자동으로 회수됩니다.
7. 평소와 다른 위치에서 관리자 역할을 요청하면 고위험 사건으로 분류됩니다.
8. 시스템은 접근을 보류하고 담당자에게 알리며, 대응 결과를 감사 로그로 남깁니다.

## 4. 범위

### 4.1 반드시 구현할 범위

- 관리·보안·업무 계정으로 구성된 AWS 3계정 구조
- Terraform으로 재현 가능한 기본 인프라
- VPC, 서브넷, 라우팅, 보안 그룹
- 개발자·보안 담당자·관리자 역할 구분
- JIT 권한 요청·승인·만료·회수
- CloudTrail 또는 표준화된 테스트 이벤트 수집
- 위험도 분류 규칙
- 탐지·대응 플레이북 3개
- 감사 로그
- 레드팀 공격 시나리오 3개
- LLM 기반 사건 요약과 대응 추천

### 4.2 후순위 범위

- 실제 GuardDuty 결과 연동
- VPC Flow Logs 연동
- IAM Access Analyzer 연동
- 간단한 운영 대시보드
- Slack 또는 Discord 알림
- 비용 현황 표시

### 4.3 제외할 범위

- 자체 SIEM 구축
- 자체 머신러닝 모델 학습
- 여러 클라우드 동시 지원
- Kubernetes 보안
- 운영 계정에 대한 무승인 자동 변경
- 실제 공격 대상에 대한 침투 테스트
- 복잡한 사내 IdP 또는 상용 IAM 제품 구현

범위를 추가하려면 기존 필수 시나리오를 훼손하지 않는지 먼저 확인하고, 팀 전체의 합의를 PR 또는 ADR로 남깁니다.

## 6. 공통 이벤트 계약

아직 GuardDuty나 SOAR를 배우지 않았더라도 모든 기능은 다음 공통 형식으로 연결합니다.

```json
{
  "event_id": "evt-001",
  "event_type": "iam.role_assume",
  "account_id": "workload-001",
  "principal": "developer-role",
  "source_ip": "203.0.113.10",
  "resource": "production-admin",
  "severity": "high",
  "occurred_at": "2026-08-18T12:00:00Z",
  "raw_event": {}
}
```

원칙:

- 이벤트 생성자는 원본 이벤트를 `raw_event`에 보존합니다.
- 이후 모듈은 공통 필드만 사용합니다.
- 실제 AWS 연동 전에는 Mock 이벤트를 사용합니다.
- 실제 연동으로 바꾸더라도 입력·출력 계약은 유지합니다.

## 7. 저장소 기본 구조

처음부터 모든 기능 파일을 만들지는 않습니다. 폴더와 문서 위치만 먼저 정하고, 구현 파일은 해당 Issue가 시작될 때 생성합니다.

```text
project/

│  ├─ ISSUE_TEMPLATE/
│  └─ workflows/
├─ docs/

├─ src/
│  └─ sentinelhub/
├─ tests/
│  ├─ fixtures/
│  ├─ unit/
```

이번 단계에서는 빈 폴더를 Git에서 유지하기 위한 최소 표시 파일만 둡니다. 실제 모듈 이름은 팀이 이벤트 계약을 확정한 뒤 결정합니다.

각 업무는 담당자·리뷰어·백업 담당자를 함께 지정합니다. 담당자가 혼자만 이해하는 구조를 만들지 않는 것이 목표입니다.

### 클라우드 담당

- Terraform
- 공통 VPC와 배포
- 계정 간 이벤트 전달

### 보안 담당 A: IAM·접근 통제

### 보안 담당 B: 탐지·대응

### 네트워크 담당

- VPC·서브넷·라우팅
- 보안 그룹
- VPC Flow Logs
- 네트워크 노출 시나리오

## 9. 개발 순서

### 단계 0: 공통 기반

- 저장소 생성
- 브랜치와 PR 규칙 적용
- Python 버전 고정
- Ruff·pytest·pre-commit 설정
- 이벤트 계약 작성
- 공격 시나리오 확정
- Mock 이벤트 생성

완료 기준: 실제 AWS 서비스 없이도 이벤트부터 보고서까지 한 번 실행됩니다.

### 단계 1: 최소 수직 흐름

```text
Mock 이벤트
→ 위험도 HIGH 판정
→ 승인 요청 생성
→ Mock 임시 권한 발급
→ 만료 처리
→ 감사 로그 저장
```

완료 기준: 한 개의 전체 흐름이 팀원 누구의 컴퓨터에서도 실행됩니다.

### 단계 2: 실제 IAM과 인프라 연결

- Terraform으로 테스트 계정 인프라 구성
- 실제 IAM 역할과 정책 적용
- JIT 권한의 실제 발급과 회수 검증
- CloudTrail 기록 확인

완료 기준: 화면의 상태뿐 아니라 AWS 실제 권한 상태가 바뀌고 복구됩니다.

### 단계 3: 탐지와 네트워크 연결

- CloudTrail 또는 GuardDuty 이벤트 연결
- IAM 권한 상승 탐지
- 비정상 역할 전환 탐지
- 보안 그룹 노출 탐지
- Flow Logs 연결

완료 기준: 준비한 공격 이벤트가 사건으로 묶이고, 탐지 근거가 남습니다.

### 단계 4: 대응과 LLM

- 플레이북 3개 구현
- 승인 게이트 추가
- 사건 요약과 위험 설명 생성
- 대응 보고서 생성
- 실패·오탐 처리

완료 기준: LLM이 잘못 판단해도 규칙과 승인 절차가 위험한 실행을 막습니다.

### 단계 5: 레드팀과 발표 준비

- RT-01, RT-02, RT-03 실행
- 탐지율과 대응 시간 측정
- 실패한 규칙 수정
- 데모 환경 초기화 절차 작성
- 발표 시나리오와 포트폴리오 자료 정리

## 10. 협업 방식

```text
Issue 생성
→ 브랜치 생성
→ 작은 작업 수행
→ 테스트 실행
→ PR 생성
→ 리뷰 1명 이상
→ CI 통과
→ main 병합
```

하나의 PR은 하루 안에 리뷰할 수 있는 크기로 제한합니다.

좋은 작업 단위:

- IAM 이벤트를 공통 형식으로 변환
- JIT 권한 요청 저장
- 만료된 권한 회수
- 특정 탐지 규칙 추가
- 특정 플레이북 추가

나쁜 작업 단위:

- 전체 보안 플랫폼 구현
- 여러 기능을 한 PR에 통합
- 테스트 없이 대규모 리팩터링

### Definition of Done

- 담당자가 아닌 사람이 실행할 수 있습니다.
- 입력과 출력이 문서화되어 있습니다.
- 정상 케이스 테스트가 있습니다.
- 실패 케이스 테스트가 있습니다.
- 로그가 남습니다.
- 실제 AWS 변경이 있다면 결과를 확인했습니다.
- 보안 영향이 PR에 기록되어 있습니다.
- 관련 문서가 업데이트되어 있습니다.

## 11. LLM 사용 규칙

모든 팀원이 서로 다른 LLM과 에이전트를 사용해도 다음 기준은 지킵니다.

- 작업 전 저장소 문서와 관련 코드를 읽습니다.
- Issue 범위를 벗어나지 않습니다.
- 기존 인터페이스를 먼저 확인합니다.
- LLM 생성 코드를 그대로 신뢰하지 않습니다.
- 보안 권한과 외부 API 호출을 사람이 검토합니다.
- 테스트를 실행하고 결과를 PR에 남깁니다.
- LLM 사용 범위를 PR에 기록합니다.
- 담당자는 제출한 코드를 설명할 수 있어야 합니다.

LLM은 코드 생성, 테스트 작성, 로그 요약, 문서 초안에 활용합니다. 권한 부여·차단 같은 실제 보안 조치는 결정적 규칙과 승인 게이트가 담당합니다.

## 12. 레드팀 검증

### RT-01: 탈취된 개발자 계정

```text
비정상 로그인
→ 운영 계정 AssumeRole
→ 민감한 S3 접근
→ 탐지·보류·세션 차단 또는 회수
```

### RT-02: IAM 권한 상승

```text
일반 역할
→ PassRole 또는 위험한 AssumeRole
→ 관리자 권한 획득 시도
→ 정책 검사·승인 없는 실행 차단
```

### RT-03: 네트워크 노출

```text
위험한 보안 그룹 규칙
→ 테스트 포트 접근
→ Flow Logs 또는 GuardDuty 확인
→ 원복 또는 IP 차단
```

모든 테스트는 별도 계정, 더미 리소스, 비파괴적인 API 호출로 제한합니다.

측정할 지표:

- 탐지율
- 평균 탐지 시간
- 평균 대응 시간
- 임시 권한 회수 성공률
- 오탐률
- 감사 로그 누락률
