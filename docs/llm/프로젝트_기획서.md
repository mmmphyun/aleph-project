# 멀티 계정 AWS 보안 대응 자동화 플랫폼

## 1. 프로젝트 한눈에 보기

이 프로젝트는 여러 개의 AWS 계정을 한 곳에서 안전하게 관리하고, 이상한 접근이 발생했을 때 사람의 승인과 자동화된 대응을 통해 피해를 줄이는 시스템을 만드는 것입니다.

쉽게 말하면 다음과 같습니다.

> 누군가 평소와 다른 방식으로 클라우드에 접근하면 이를 발견하고, 위험한 권한은 잠시만 허용하며, 문제가 생기면 자동으로 차단하고 기록하는 보안 관제 시스템입니다.

프로젝트명은 다음과 같이 사용할 수 있습니다.

**SentinelHub: 멀티 계정 AWS 환경을 위한 위험 기반 JIT 접근제어 및 보안 대응 자동화 플랫폼**

## 2. 왜 필요한가

클라우드에서는 아이디와 비밀번호만 지키면 끝나는 것이 아닙니다. 누가 어떤 계정에 접근했는지, 어떤 권한을 사용했는지, 평소와 다른 행동을 했는지를 계속 확인해야 합니다.

예를 들어 개발자가 운영 서버를 잠깐 점검해야 한다고 가정합니다. 항상 관리자 권한을 주면 편하지만, 계정이 탈취되었을 때 공격자도 관리자 권한을 갖게 됩니다.

그래서 이 프로젝트에서는 다음 방식을 사용합니다.

- 평소에는 최소한의 권한만 부여합니다.
- 꼭 필요한 작업이 있을 때만 추가 권한을 요청합니다.
- 승인된 경우에도 일정 시간 동안만 권한을 줍니다.
- 작업이 끝나거나 시간이 지나면 권한을 자동으로 회수합니다.
- 모든 요청과 결과를 기록합니다.

## 3. 핵심 용어

### 멀티 계정

AWS를 하나의 계정으로만 운영하지 않고 여러 계정으로 나누는 방식입니다.

- 관리 계정: 전체 조직을 관리합니다.
- 보안 계정: 로그와 보안 이벤트를 모읍니다.
- 업무 계정: 실제 애플리케이션과 서버가 실행됩니다.

계정을 나누면 한 계정에 문제가 생겨도 전체 환경으로 피해가 번지는 것을 줄일 수 있습니다.

### IAM

IAM은 AWS에서 “누가 무엇을 할 수 있는가”를 정하는 출입증 관리 시스템입니다.

### JIT 권한

JIT는 Just-In-Time의 약자입니다. 필요한 사람에게 필요한 작업 동안만 임시 권한을 주는 방식입니다.

예를 들어 “운영 서버 점검을 위해 30분 동안만 읽기 권한을 요청한다”와 같습니다.

### SOAR

SOAR는 보안 사고가 발생했을 때 정해진 대응 절차를 자동으로 실행하는 방식입니다.

예를 들어 위험한 로그인이 발견되면 계정을 잠그고, 담당자에게 알림을 보내고, 사건 기록을 만드는 작업을 자동으로 수행합니다.

## 4. 목표 아키텍처

```text
[관리 계정]
 조직·계정·공통 정책 관리

[보안 계정]
 CloudTrail / GuardDuty / 이벤트 수집
             ↓
       EventBridge
             ↓
  위험도 판단 및 대응 정책
             ↓
 승인 요청 / 권한 회수 / 차단 / 알림

[업무 계정]
 애플리케이션·서버·S3 등 실제 업무 리소스
```

각 서비스의 역할은 다음과 같습니다.

- AWS Organizations: 여러 AWS 계정을 묶어 관리합니다.
- IAM Identity Center: 사용자가 계정과 역할에 접근하는 통로입니다.
- CloudTrail: AWS에서 누가 어떤 작업을 했는지 기록합니다.
- GuardDuty: 의심스러운 보안 활동을 탐지합니다.
- EventBridge: 보안 이벤트를 다음 처리 단계로 전달합니다.
- Lambda 또는 Step Functions: 대응 절차를 실행합니다.
- S3 또는 DynamoDB: 사건과 감사 기록을 저장합니다.
- 대시보드 또는 알림 채널: 담당자에게 상황을 보여줍니다.

## 5. 반드시 구현할 기능

### 5.1 계정과 인프라

- 관리·보안·업무 계정 3개 구조
- VPC, 서브넷, 라우팅, 보안 그룹
- Terraform으로 재현 가능한 배포
- 로그를 중앙에서 확인할 수 있는 구조

### 5.2 접근 통제

- 개발자·보안 담당자·관리자 역할 분리
- 최소권한 정책
- 운영 계정 접근 요청
- 승인 후 임시 권한 발급
- 시간 만료 후 자동 회수
- 권한 발급과 회수 이력 기록

### 5.3 탐지와 대응

- 비정상 로그인 탐지
- 계정 간 위험한 역할 전환 탐지
- 민감한 S3 접근 탐지
- 위험한 IAM 권한 사용 탐지
- 인터넷에 과도하게 노출된 네트워크 탐지

### 5.4 LLM 활용

LLM은 다음 일을 보조합니다.

- Terraform과 Lambda 코드 초안 생성
- 로그 분석 및 사건 요약
- 위험한 이유를 쉬운 문장으로 설명
- 대응 플레이북 추천
- 테스트 데이터와 테스트 코드 생성
- 최종 보고서 작성

LLM이 바로 권한을 부여하거나 운영 환경을 무조건 차단하지는 않습니다. 실제 조치는 규칙과 승인 절차를 통과해야 합니다.

## 6. 공격 시나리오

### 시나리오 A: 탈취된 개발자 계정

```text
비정상 위치에서 로그인
→ 운영 계정 역할 접근 시도
→ 민감한 S3 접근
→ 사건 생성
→ 세션 차단 또는 권한 회수
```

### 시나리오 B: IAM 권한 상승

```text
일반 개발자 역할
→ 위험한 AssumeRole 또는 PassRole 시도
→ 관리자 권한 획득 시도
→ 탐지 및 승인 없는 실행 차단
```

### 시나리오 C: 네트워크 노출

```text
인터넷에 열린 보안 그룹
→ 비정상 포트 접근
→ Flow Logs 또는 GuardDuty 이벤트
→ 보안 그룹 수정 또는 IP 차단
```

공격은 반드시 별도 테스트 계정과 더미 리소스에서 수행합니다. 데이터 삭제, 실제 자격증명 탈취, 외부 시스템 공격은 하지 않습니다.

## 7. 팀 역할

- 보안 담당자 1: IAM 정책, 최소권한, JIT 권한 설계
- 보안 담당자 2: 로그 분석, 탐지 규칙, SOAR 플레이북
- 클라우드 담당자: 멀티 계정 구조, Terraform, 배포, 운영 문서
- 네트워크 담당자: VPC, 라우팅, 보안 그룹, Flow Logs, 네트워크 공격 시나리오

모든 팀원은 LLM을 사용해 구현할 수 있지만, 자신이 맡은 결과물이 실제로 어떤 위험을 줄이는지는 설명할 수 있어야 합니다.

## 9. 성공 기준

최종 발표에서 다음 흐름을 실제로 시연할 수 있어야 합니다.

1. 정상 사용자는 정상 작업을 수행합니다.
2. 공격자가 위험한 접근을 시도합니다.
3. 시스템이 해당 활동을 탐지합니다.
4. LLM이 사건과 위험 이유를 설명합니다.
5. 승인 없이는 고위험 권한이 발급되지 않습니다.
6. 임시 권한은 시간이 지나면 회수됩니다.
7. 대응 결과와 담당자 행동이 감사 로그에 남습니다.
8. 오탐일 때 관리자가 원상 복구할 수 있습니다.
