# 레드팀 검증 계획

## 1. 목적

이 문서는 프로젝트가 실제 공격 흐름을 발견하고 대응할 수 있는지 확인하기 위한 테스트 계획입니다.

레드팀은 공격자 역할을 맡고, 블루팀 시스템은 이를 탐지하고 대응합니다. 목표는 시스템을 망가뜨리는 것이 아니라 다음을 검증하는 것입니다.

- 위험한 행동을 발견하는가?
- 발견한 사건을 이해하기 쉽게 설명하는가?
- 권한을 적절하게 제한하거나 만료·무효화하는가?
- 정상 사용자를 불필요하게 막지 않는가?
- 모든 과정이 기록되는가?

## 2. 안전 규칙

- 테스트용 AWS 계정에서만 실행합니다.
- 실제 비밀번호나 액세스 키를 사용하지 않습니다.
- S3에는 더미 데이터만 저장합니다.
- 데이터 삭제, 암호화 키 삭제, 서비스 중단 테스트는 하지 않습니다.
- 공격 코드는 위험한 페이로드 없이 권한 요청과 API 호출 수준으로 제한합니다.
- 테스트가 끝나면 리소스와 권한을 정리합니다.
- CloudTrail Fixture에는 비식별화한 테스트 데이터만 사용합니다.

## 3. 정상 행동 기준선

먼저 다음 정상 행동을 기록합니다.

- 개발자가 업무 계정에서 읽기 작업을 수행
- 보안 담당자가 보안 계정에서 로그를 조회
- 승인된 개발자가 30분 동안 운영 리소스를 점검
- 네트워크 담당자가 테스트용 보안 그룹을 수정

정상 행동을 정의하지 않으면 정상 작업과 공격을 구분할 수 없습니다.

## 4. 테스트 시나리오

### RT-01 비정상 로그인과 운영 계정 접근

**공격 흐름**

1. 개발자 역할로 테스트 로그인
2. 평소와 다른 IP 또는 시간대의 이벤트 생성
3. 운영 계정 역할 AssumeRole 시도
4. 테스트용 S3 버킷 접근

**기대 결과**

- 비정상 로그인 이벤트가 탐지됩니다.
- 계정과 역할 전환 정보가 사건에 연결됩니다.
- 고위험 접근은 차단되거나 승인 대기 상태가 됩니다.
- 담당자에게 알림이 전달됩니다.
- 사건의 모든 단계가 감사 로그에 남습니다.
- 이벤트 발생부터 대응 완료까지의 지연 시간이 측정됩니다.

### RT-02 IAM 권한 상승 시도

**공격 흐름**

1. 일반 개발자 역할 사용
2. 위험한 PassRole 또는 AssumeRole 요청
3. 관리자 권한 획득을 시도

**기대 결과**

- 위험한 IAM 작업이 탐지됩니다.
- 정책 검사 결과가 표시됩니다.
- 승인되지 않은 권한 상승이 거부됩니다.
- Session Policy가 `iam:CreateUser`, `iam:CreateAccessKey`, `iam:PassRole` 등 영구 백도어 경로를 제한합니다.
- LLM이 위험한 이유를 설명합니다.
- 기존 정상 작업은 계속 허용됩니다.

### RT-03 네트워크 노출

**공격 흐름**

1. 테스트용 보안 그룹에 위험한 인바운드 규칙 생성
2. 테스트 포트에 접근
3. VPC Flow Logs 또는 GuardDuty 이벤트 확인

**기대 결과**

- 위험한 보안 그룹 변경이 탐지됩니다.
- 이벤트가 해당 계정과 리소스에 연결됩니다.
- 승인된 플레이북이 위험한 보안 그룹 규칙을 원상 복구합니다.
- 원복 결과가 기록됩니다.

## 5. 측정 지표

| 지표 | 의미 |
|---|---|
| 탐지율 | 준비한 공격 중 발견한 비율 |
| 평균 탐지 시간 | 공격 발생부터 사건 생성까지 걸린 시간 |
| 평균 대응 시간 | 사건 생성부터 승인·원복·무효화까지 걸린 시간 |
| TTL 만료 성공률 | 임시 권한이 예정된 시간에 만료된 비율 |
| 긴급 무효화 영향 | 무효화된 세션과 영향을 받은 세션의 범위 |
| 오탐률 | 정상 행동을 공격으로 판단한 비율 |
| 감사 로그 누락률 | 과정 중 기록되지 않은 행동의 비율 |
| 이벤트 지연 시간 | 이벤트 발생부터 처리 대상 도착까지 걸린 시간 |

## 6. 실패했을 때 확인할 것

- 이벤트가 CloudTrail에 기록되었는가?
- 올바른 계정의 EventBridge로 전달되었는가?
- 이벤트 패턴이 실제 JSON 구조와 일치하는가?
- Lambda 또는 Step Functions가 필요한 권한을 갖고 있는가?
- 대응 후 실제 IAM 상태가 바뀌었는가?
- TTL 만료 후 임시 세션이 더 이상 동작하지 않는가?
- 긴급 무효화가 같은 역할의 다른 세션에 미친 영향이 문서화되었는가?
- Session Policy가 영구 백도어 생성 경로를 제한하는가?
- 대시보드만 바뀌고 AWS의 실제 상태는 바뀌지 않은 것은 아닌가?

## 7. 최종 발표 순서

1. 정상 작업 수행
2. 공격 시나리오 실행
3. 탐지 이벤트 표시
4. LLM의 사건 요약 확인
5. 승인 없는 접근 차단
6. JIT 권한 승인
7. 제한 시간 후 자동 만료
8. 감사 로그와 측정 지표 확인
9. 필요 시 긴급 무효화와 영향 범위 확인
10. 오탐·실패·한계 설명

성공한 테스트만 보여주는 것보다, 실패했던 탐지 규칙과 개선 과정까지 설명하는 편이 기술적으로 더 신뢰도 높은 포트폴리오가 됩니다.
