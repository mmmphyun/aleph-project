# ADR 0001: 단일 AWS 계정 내 VPC 격리 구조 채택

- **상태**: 승인됨 (Accepted)
- **결정자**: 클라우드 A (테크 리드 @mmmphyun)
- **일자**: 2026-09-03
- **소유 직무**: 클라우드 A (인프라/플랫폼)

---

## 1. 배경 및 문제 제기 (Context)

- CloudShield 프로젝트는 모의 공격(Kali/Hydra), 타깃 서버(EC2), 탐지/오케스트레이터(Lambda), 보안 통제(WAF/SG)가 유기적으로 연동되는 파이프라인을 구축해야 함.
- 초기 인프라 설계 시 엔터프라이즈 멀티 계정(공격자 계정, 타깃 인프라 계정, 보안 관제 계정 분리) 모델을 적용할 경우:
  - 계정 간 IAM AssumeRole 구성, AWS Organizations 거버넌스, Transit Gateway/VPC 피어링 라우팅 설정 등 인프라 부트스트래핑 복잡도가 과도하게 증가함.
  - 4명의 팀원이 로컬 개발 및 E2E 테스트를 수행할 때 교차 계정 권한 문제로 인해 심각한 작업 병목(Deadlock)이 발생할 위험이 높음.

---

## 2. 대안 검토 및 트레이드오프 분석 (Considered Options)

| 구분 | 방안 1: AWS Organizations 멀티 계정 분리 | 방안 2: 단일 계정 내 VPC 서브넷 격리 (채택) |
| :--- | :--- | :--- |
| **격리 수준** | 계정 단위 완벽한 IAM/빌링 격리 | VPC 서브넷 및 Security Group 단위 논리적 격리 |
| **설정 복잡도** | 매우 높음 (AssumeRole, Organizations, RAM, TGW) | 낮음 (단일 VPC 내 Public/Private Subnet 및 Bastion) |
| **개발 및 테스트 속도** | 계정 간 권한 디버깅으로 개발 지연 발생 | **단일 크레덴셜로 빠른 로컬 검증 및 Moto 테스트베드 구축 용이** |
| **비용 및 리소스** | 계정별 최소 리소스 및 관리 오버헤드 증가 | 단일 계정 내 리소스 최소화로 프리티어 및 예산 통제 용이 |

---

## 3. 아키텍처 결정 (Decision)

- **단일 AWS 계정 내 논리적 VPC 격리 모델 채택**:
  - 공격자 인스턴스와 타깃 인스턴스, 관제 인프라를 단일 AWS 계정에 배치하되, VPC 서브넷과 라우팅 테이블 및 Security Group으로 트래픽을 엄격히 격리함.
  - 외부 접근은 Bastion Host 또는 SSM Session Manager를 통해서만 허용.
  - 불필요한 교차 계정 인증 병목을 원천 제거하고, 단일 10초 관통 E2E 데모 검증에 집중함.

---

## 4. 기대 효과 및 결과 (Consequences)

- **긍정적 영향**:
  - 팀원 간 IAM 권한 마찰 제거로 온보딩 및 로컬 개발 속도 극대화.
  - Terraform 코드 단순화 및 `moto` 기반의 통합 로컬 테스트베드 구현 용이.
- **관리 대상 한계점**:
  - 단일 계정 IAM 관리 권한 공유에 따른 실수 방지를 위해 권한 분리 및 Terraform 상태 잠금(State Lock) 철저 관리 필요.
